# Design system and product profile

The **brand profile** (a *design system*) and the **product profile** (a *product map*) are the two documents the design-system feature builds, imports, approves and feeds to agents. This file is the **internal design record** for that feature: it is **not published** — it stays in the repository and the platform assistant searches it as *internal background*. Nothing here is a customer promise; the customer-facing page is [`user-guide/design-system.md`](user-guide/design-system.md).

## Data model

The feature is backed by **five API-owned tables**: `design_systems`, `design_system_versions`, `design_system_sources`, `design_system_change_proposals` and `design_system_library_assets`. Columns are `snake_case`, enums are persisted **by name** (`.HasConversion<string>()`, max 40) and are **append-only**, ids are `uuid`, and timestamps are `timestamp with time zone` in UTC. None of these five tables carries the named `Tenant` query filter: they are guarded at a parent instead (the project for project routes, the organization's library row for library containers and library assets; see **Tenancy**) and are registered in the unfiltered-table list of `TenantBoundaryInventoryTests`. The only filtered table in this feature is `design_system_libraries`.

`design_systems` — one row per project per kind.

| Column | Type / notes |
|--------|--------------|
| `id` | `uuid` |
| `project_id` | `uuid` NULL, FK `projects` `ON DELETE CASCADE` |
| `kind` | `design` or `product_map`, CHECK `kind IN ('design','product_map')` |
| `name` | varchar(200) |
| `current_version_id` | `uuid` NULL — the **Approved** version agents use |
| `watch_json` | jsonb NULL |
| `parent_library_id` | Phase 4 — `uuid` NULL, the **brand library** this profile inherits from; a database **CHECK** guards the reference (see **Brand library**) |
| `created_by_user_id` | `uuid` |
| `created_at` / `updated_at` | `timestamp with time zone` UTC |

UNIQUE(`project_id`,`kind`).

`design_system_versions` — immutable except `state` and the `approved_*` columns.

| Column | Type / notes |
|--------|--------------|
| `id` | `uuid` |
| `design_system_id` | `uuid` FK `design_systems` |
| `version_number` | int (1, 2, 3…); UNIQUE(`design_system_id`, `version_number`) |
| `state` | `Draft` / `Approved` / `Superseded` / `Rejected` |
| `document_json` | jsonb |
| `document_digest` | char(64) lowercase hex SHA-256 |
| `origin` | `Import` / `StaticExtract` / `LlmExtract` / `Manual` / `Merge` / `Restore` |
| `base_version_id` | `uuid` NULL |
| `workflow_execution_id` | `uuid` NULL — **NO FK** |
| `coverage_json` | jsonb NULL |
| `created_by_user_id` | `uuid` |
| `approved_by_user_id` / `approved_at` | NULL until approved |
| `created_at` | `timestamp with time zone` UTC |

At most **one Approved version per system** (the previous one becomes `Superseded` in the same transaction); `Rejected` and `Superseded` versions are kept forever (append-only); a **Restore** is a new version with `origin=Restore`, never a mutation of an existing row.

`design_system_sources` — one row per imported or watched source, written for the version that read it.

| Column | Type / notes |
|--------|--------------|
| `id` | `uuid` |
| `design_system_id` / `version_id` | `uuid` — the version these bytes were read for |
| `project_file_id` | `uuid` NULL — the live `project_files` row, when the source is a project file |
| `source_kind` | `ProjectFile` / `GitHubPath` / `Upload` / `Url` / `Figma` / `Manual` |
| `path` | varchar(1024) |
| `importer` | varchar(64) — the importer id that read it, or `product-map` for a static-extracted map |
| `content_sha256` | char(64), computed **SERVER-SIDE** — the digest the **approved version** was read from |
| `source_revision` | varchar(128) |
| `size_bytes` | bigint |
| `status` | `Current` / `Changed` / `Missing` — the drift check's own bookkeeping, never a rewrite of `content_sha256` |
| `last_checked_at` / `last_changed_at` | `timestamp with time zone` UTC |

`design_systems.watch_json` optionally carries `{"globs": [...]}`; when it is absent or malformed the drift check falls back to six first-party design globs (`**/*.css`, `**/tailwind.config.*`, `**/*.tokens.json`, `**/tokens/**/*.json`, `**/DESIGN.md`, `**/brand/**`).

`design_system_change_proposals` — one row per change the drift check (or a manual check) prepared; **Phase 2 creates the table, Phase 3 fills it**.

| Column | Type / notes |
|--------|--------------|
| `id` | `uuid` |
| `design_system_id` | `uuid` FK `design_systems` |
| `base_version_id` | `uuid` — the version the check compared against (the approved one) |
| `proposed_version_id` | `uuid` — the `StaticExtract` Draft the check wrote |
| `trigger` | `SourceChanged` / `Manual` / `Scheduled` / `Import` |
| `drift_score` | double precision, 0..1 (formula under **Drift**) |
| `diff_json` | jsonb — `DesignDocumentDiffer` / `ProductMapDiffer` output, plus the score |
| `status` | `Pending` / `Approved` / `Rejected` / `Superseded` / `Expired` |
| `proposed_digest` | char(64) — the digest of the proposed document, also the suppression key |
| `decided_by_user_id` / `decided_at` / `decision_note` | NULL until a person decides |
| `created_at` | `timestamp with time zone` UTC |

At most **one Pending proposal per system**: a newer check supersedes the older Pending ones in the same transaction. A proposal whose `proposed_digest` matches a Pending proposal, or a Rejected one decided within the suppression window, is not raised at all.

`design_system_library_assets` — one row per SVG or font file an organization's brand library owns (T-010).

| Column | Type / notes |
|--------|--------------|
| `id` | `uuid` |
| `library_id` | `uuid` FK `design_system_libraries` `ON DELETE CASCADE` |
| `name` | varchar(200), sanitized; UNIQUE(`library_id`,`name`) |
| `mime_type` | varchar(100) — `image/svg+xml` or one of `font/woff`, `font/woff2`, `font/ttf`, `font/otf` |
| `size_bytes` | bigint — the size of the **stored** bytes (the sanitized SVG, not the upload) |
| `sha256` | char(64) — lowercase hex of the stored bytes, computed server-side |
| `storage_key` | varchar(1024) — `design-libraries/{orgId}/{libraryId}/assets/{assetId}/{name}` |
| `role` | varchar(20) NULL — `logo`, `icon`, `preview` or `font` |
| `variant` | varchar(40) NULL |
| `created_by_user_id` | `uuid` |
| `created_at` | `timestamp with time zone` UTC |

The table carries **no organization column and no `Tenant` filter**: the organization is proven one FK up by the library lookup every route performs first, and the row cascades when the library is deleted. A project's design document may name an asset of its own linked library by `library-asset:<guid>` (see **Documents**); a library container names its own assets the same way.

**Engine-owned additions.** The WorkflowEngine owns `workflow_executions.design_system_pin_json` (jsonb NULL, ENGINE migration `AddExecutionDesignSystemPin`) and `workflow_steps.design_system_config_json` (jsonb NULL, ENGINE migration `AddDesignSystemStep`). The engine maps `design_systems` and `design_system_versions` **read-only** through `ExcludeFromMigrations()`: it reads only `versions.id`, `version_number`, `design_system_id`, `state`, `document_json`, `document_digest` and `design_systems.project_id`, `kind`, and it never writes them.

## Brand library

Phase 4 adds the **organization brand library**: a `design_systems` row of `kind = 'design'` that belongs to an organization instead of one project, so every project in a team can inherit the same brand. A project's design system names its library through `design_systems.parent_library_id`; the **CHECK** on that column guards the self-reference. Resolution reads the parent library first and the project profile over it, so a project may add tokens and override inherited ones, but a token the owner **locked** stays at the top of the merge precedence (**Documents**) and a child cannot delete a parent token (**no tombstones**). The project design-system summary carries `parentLibrary` (`{id, name}`) when the profile inherits from a library. Library names are unique within an organization (`409 library_name_taken` on create and rename), an organization holds at most `DesignSystem:Library:MaxPerOrganization` libraries (default `50`; beyond that `409 library_limit_reached`), and moving a project to another organization clears its `parent_library_id`, so the link never follows a project out of the organization that owns the library.

Tenancy follows the platform's two-part rule. Because a library can be addressed by an id the caller chooses, the named `Tenant` query filter sits on `design_system_libraries` (the library row, owned by one organization). `design_systems` and its three child tables (`design_system_versions`, `design_system_sources`, `design_system_change_proposals`) carry **no filter**: project routes guard them at the project, and a library's document container (a `design_systems` row with no project) is reached only after the organization-scoped library lookup in `OrgDesignLibrariesController`. See **Tenancy**.

## Documents

Both profiles are **JSON objects**, stored **canonical**, and each has a maximum serialized size of **256 KiB** (`262144` bytes).

The **design document** uses schema `reelbolt.design-system/1`. All top-level keys are optional except `schema`: `schema`, `name`, `color`, `typography`, `spacing`, `radius`, `shadow`, `motion`, `component`, `z`, `modes`, `voice`, `assets`, `fonts`. A **TOKEN** is an object with `$value`; a **GROUP** is an object without `$value`. A token carries `$type` (required), `$value`, an optional `$description` (≤ 200 chars, sanitized) and an optional `$extensions.com.reelbolt` provenance object `{method, importer, sourceId, loc, conf (0..1), locked, orig}`. `$type` values include `color`, `dimension`, `fontFamily`, `fontWeight`, `duration`, `cubicBezier`, `number`, `shadow`, `typography` and `keyword` (a lowercase word matching `^[a-z][a-z0-9-]{0,39}$`, used for a text transform). An alias is a string such as `"{color.brand.primary}"`: its target must exist, have the same `$type`, sit at depth ≤ 8 and form no cycle. A `shadow` value may be an **empty array**, which is how a CSS `none` shadow is stored. The `z` group holds stacking-order `number` tokens. `modes` uses the name pattern `^[a-z][a-z0-9-]{0,23}$`, at most **6 modes** with at most **500 overrides** each. `voice` holds lists: `summary` ≤ 600, `tone` ≤ 80 × ≤ 12, `do`/`dont` ≤ 140 × ≤ 12, `taglines` ≤ 120 × ≤ 10, `vocabulary` ≤ 40 × ≤ 30. Each of `assets.logo`, `assets.icon` and `assets.preview`, and each entry of its `variants`, may also carry these optional keys (closed enums, anything else is `DS_V15`): `file` (sanitized original file name, at most 200 characters), `subject` (`product|publisher|unknown`), `form` (`mark|wordmark|lockup`), `tone` (`dark|light|mid`), `readableOn` (at most two distinct values from `light`, `dark`) and `luminance` (a number from 0 to 1). A document without them stays valid. `assets.logo`, `assets.icon` and `assets.preview` `fileRef` values are `project-file:<guid>` (a file in the **SAME project**) or `library-asset:<guid>` (an asset of the library the profile descends from, or of the library container itself). `fonts` holds `licence` (family → licence text, `unknown` when the source named a family but no licence), `resolved` (family → one of the bundled sandbox font names) and `files` (family → `project-file:<guid>`, at most 20). **No URLs anywhere in a document.**

The **product map** uses schema `reelbolt.product-map/1`. It replaces the output of `CodeStructureAnalyzer`, `DependencyAnalyzer`, `ComponentInventoryAnalyzer` and `RouteAndApiAnalyzer`. Its top-level fields are `schema`; `name` (≤ 120); `framework` (name enum `next|react|vite|remix|nuxt|vue|svelte|angular|astro|express|other`, `version` ≤ 30, `language` `typescript|javascript|mixed|other`, `styling` ≤ 30 × ≤ 8, `packageManager` `npm|pnpm|yarn|bun|unknown`, `projectType` ≤ 40); `architecture` ≤ 600; `routingStrategy` ≤ 120; `directories` (≤ 20); `entryPoints` (≤ 30); `routes` (≤ 300, each with `path`, `file`, `kind` `page|layout|api|other`, `method`, `title`, `requiresAuth`, `source` `static|llm|manual`); `components` (≤ 300, each with `name`, `path`, `responsibility`, `keyProps` ≤ 40 × ≤ 8, `core`, `source`); `dependencies` (runtime ≤ 150, dev ≤ 100, ui ≤ 40); `patterns` ≤ 120 × ≤ 12; `previewCards` (≤ 100, each with `name` ≤ 80, `group` ≤ 80, `subtitle` ≤ 160, `viewport` ≤ 20, `path` ≤ 200, `text` ≤ 500, at most 8 relative `assets`, and `runtimeRendered`); and `provenance` (per section, `method static|llm|manual|mixed` plus `sourceIds`).

**Canonical JSON** is produced by `CanonicalJson.Serialize`. Object keys are sorted ordinal ascending, recursively; there is no insignificant whitespace; strings are escaped with the default `System.Text.Json` encoder, so `<`, `>`, `&` and `'` become `&lt;`, `&gt;`, `&amp;` and `&apos;` (`JavaScriptEncoder.UnsafeRelaxedJsonEscaping` is **NOT** used). Integers are written without a decimal point, doubles via `double.ToString("R", InvariantCulture)`, `-0` is normalized to `0`, and arrays keep their order. `document_digest` is the lowercase hex SHA-256 of that canonical serialization and is **ALWAYS recomputed by the server**; a client-supplied digest is ignored.

`DesignText.Sanitize(string?, int maxLength)` drops the brackets `[` `]`, the quote `"`, the backslash `\`, the backtick, the angle brackets `<` `>`, the braces `{` `}` and `#`, the fullwidth and CJK lookalikes of those characters (for example U+FF3B, U+3010, U+FF1C), plus Unicode format characters (zero-width, bidi), the tag block U+E0000..U+E007F, variation selectors (U+FE00..U+FE0F, U+E0100..U+E01EF) and U+FFFD; it collapses control characters and whitespace runs to one space; then trims, caps at `maxLength` and returns `null` if nothing is left.

**Coverage** is stored in `coverage_json` and computed by `DesignCoverage.Compute`: `design.fallbackRecommended` = NOT (primaryColor AND typography AND tokenCount ≥ 8); `productMap.fallbackRecommended` = (components == 0) OR (routes == 0 AND framework.name == "other") OR (responsibilityFilledPct < 0.5).

**Merge precedence** is `DesignDocumentMerger`. Per token path the highest wins: (1) `locked=true` in the base, (2) an imported token file, (3) a static repo parse, (4) the LLM, (5) nothing. Ties inside a level go to the higher `conf`, then to the earlier layer. The output is re-canonicalized and re-validated.

## Importers

Thirteen importers ship. They implement `IDesignImporter`, are addressed by the id below, and report an `importer` id onto every source reference they read. Eight of them are in `DesignImportRegistry.All`; the other five (`figma-variables`, `brand-pdf`, `penpot`, `sketch`, `claude-design`) are reached through their own route or through `BundleImporter`.

| Id | Accepts | Axes it fills | Since |
|----|---------|---------------|-------|
| `dtcg` | DTCG JSON, the 2025.10 `$value`/`$type` dialect or the legacy Style Dictionary `value`/`type` form | tokens (full), derived tokens (partial) | Phase 2 |
| `css-theme` | CSS custom properties plus Tailwind v4 `@theme` | tokens (full), modes (partial), derived tokens (full) | Phase 2 |
| `design-md` | `DESIGN.md`, or Markdown with YAML front matter containing `colors:` or `typography:` | tokens (partial: YAML front matter only, never colours or fonts written in prose or tables), voice (full), derived tokens (partial) | Phase 2 |
| `tokens-studio` | Tokens Studio JSON exports (sets/themes; skipped mode tokens become the `MODE_TOKEN_SKIPPED` diagnostic, an ignored theme block `THEME_IGNORED`) | tokens (full), modes (full), derived tokens (partial) | Phase 3 |
| `shadcn-registry` | a shadcn registry JSON document | tokens (full), modes (partial), derived tokens (partial) | Phase 3 |
| `storybook-index` | a Storybook `index.json` catalogue | components (full) | Phase 3 |
| `style-dictionary` | a Style Dictionary JSON config, whose `source` globs select the token files handed to `dtcg`; a JavaScript or TypeScript config is never executed | tokens (full), derived tokens (partial) | — |
| `tailwind-v3` | a Tailwind v3 `tailwind.config.*` read as inert text by the restricted `JsLiteralParser`; reached from a project's own files, **not from a zip** (see **Zip bundles and vendor layouts**) | tokens (full), derived tokens (partial) | — |
| `figma-variables` | Figma variables, fetched **once** by `FigmaVariablesClient` from the fixed Figma REST endpoint after the route's `Import:Figma:Enabled` check (403/404/redirect answers are mapped, redirects never followed) | tokens (full), modes (full), derived tokens (partial) | Phase 3 |
| `brand-pdf` | a brand-guide PDF, whose text is extracted only by the `import-worker` (see **Import worker**) | tokens (partial), fonts (partial) | Phase 3 |
| `penpot` | a Penpot `.penpot` v3 archive's JSON library objects (`colors`/`tokens`/`tokensLib`/`typography`), dispatched by `BundleImporter`; Penpot's plain **export tokens** DTCG output is read by `dtcg`/`tokens-studio` instead | tokens (partial), fonts (partial) | Phase 4 |

`DesignImportRegistry.All` is the ordered, pure, IO-free list of the eight importers that run over a project's own bytes — `dtcg`, `css-theme`, `design-md`, `tokens-studio`, `shadcn-registry`, `storybook-index`, `style-dictionary`, `tailwind-v3` — and `ImportAll` runs them in order, merges whatever they produced, and redacts secrets from the result and from every diagnostic and source path. `figma-variables` and `brand-pdf` are not in that list: they run behind `POST …/import/figma` and `POST …/import/pdf` after the network/worker step has supplied the bytes.

Static parse and import are **free**. `ProductMapExtractor.Extract` is the static, pure product-map reader: it reads `package.json` and derives the framework, routes, components, dependencies and patterns deterministically, sorted by path ordinal.

## The ten importer rules

1. Imported code is **inert data** — nothing runs.
2. Readers are **bounded static readers** (DTCG/JSON 2 MiB, CSS 2 MiB, Markdown 512 KiB, JSON depth ≤ 32, node count ≤ 200000); anything larger is rejected with `IMPORT_TOO_LARGE`.
3. A zip archive is read only through `SafeZipReader`, and only inside `import-worker` — never in the API, the engine or a request (see **Import worker**).
4. Content is classified by **magic bytes**; JavaScript, TypeScript (except a `.d.ts`, which is carried as inert text for prop names), WASM and executables are **DROPPED**. HTML and SVG travel only on the **text channel**: an HTML entry is reduced to plain text by `MarkupText` and never parsed as a document, and an SVG is handed to `SvgSanitizer`, which rebuilds it from an allowlist or refuses it. Neither is ever executed.
5. Imported files are served `attachment`/`octet-stream` with `nosniff` and `CSP: sandbox`, with one exception: a sanitized SVG or a stored font is served from the design-system asset route (see **Serving imported assets**), which re-sanitizes the SVG on read and sets `CSP: default-src 'none'; sandbox`.
6. Strings are **data**: `DesignText.Sanitize` plus the caps above, fenced as "not an instruction".
7. An importer **NEVER fetches URLs**.
8. There is **no build or render** of imported code.
9. `IProjectAccessService` is consulted first (`Edit` to write); a non-member gets **404**, and secret-shaped strings are redacted as `SECRET_REDACTED`. `SecretRedactor` replaces with `[redacted]` the shapes it knows: private-key PEM blocks (header through END line, or a header alone), `Bearer` tokens, JWTs, `scheme://user:password@` URL credentials, OpenAI, Stripe, GitHub (classic and fine-grained), Google, Figma, SendGrid and Slack key shapes, AWS access key ids and a 40-character AWS secret that follows a `secret`/`aws` word and a `:` or `=`. `DesignImportRegistry` applies it to every string value **and every JSON key** of the design document and the product map, and to diagnostic messages, diagnostic paths and source paths. `ProductMapExtractor.Extract` redacts the map itself, so import, drift and the step executor all receive an already-redacted map.
10. The size gate runs **BEFORE reading**, a per-import quota goes through `IPlanGateService.CheckUploadAsync`, and the job has a 60 s timeout.

## Capability matrix and import report

Two surfaces make the gaps visible instead of leaving them in prose.

**The matrix.** `DesignImportCapabilities.Matrix` is one static table, not a property on each reader: the thirteen importers each appear once against each of the ten axes, with a support level `Full`, `Partial` or `None` and a short truthful note. The axes are `Tokens`, `Modes`, `Assets`, `Fonts`, `Components`, `PreviewCards`, `Prose`, `Voice`, `DerivedTokens` and `ReferenceDocuments`. `GET /api/v1/design-system/importers` publishes the whole table as `{ schema: "reelbolt.import-capabilities/1", importers: [{ id, label, axes: [{ axis, support, note }] }] }`; the route takes no project id and answers every authenticated caller the same payload. A drift test fails the build when an importer gains or loses a row, so the table cannot fall behind the code.

**The report.** The zip, Figma and PDF import responses carry `report`; the project-file import (`POST …/import`) returns no report (`report` is null), because `DesignSystemService` returns only the created versions and a report built from a null document would claim every axis imported 0 with support `None`. `DesignImportReportBuilder.Build` counts the result into one row per axis:

- `imported` — tokens found, modes, kept assets, font entries, product-map components, preview cards, voice present and reference documents. Derived tokens are the destinations actually present in the document: every token in the `z` group, every `keyword` token and every `shadow` token whose value is the empty array. A resolved `color-mix()` becomes an ordinary colour token and is not counted there, and a clean resolution emits no diagnostic at all.
- `dropped` — **only genuine losses**. `DesignImportReportBuilder.IsDropDiagnostic` counts every `Warn` and `Error`, and an `Info` only when its code names a removal: the fixed list `CLAUDE_DESIGN_FILE_SKIPPED`, `BUNDLE_MARKUP_NOT_READ`, `CSS_TOKEN_UNMAPPED`, `ALIAS_UNRESOLVED`, `SD_INCLUDE_IGNORED`, `SD_NON_JSON_SOURCE`, `UNSAFE_FONT`, `NO_TOKENS_RECOGNIZED`, `SKETCH_NO_LIBRARY`, `PENPOT_NO_LIBRARY`, or any code ending in `_SKIPPED`, `_TOO_LARGE`, `_CAP`, `_DROPPED`, `_REFUSED`, `_QUARANTINED`, `_NOT_UPLOADED` or `_NOT_CREATED`. The success/summary `Info` codes (`CLAUDE_DESIGN_ASSETS`, `CLAUDE_DESIGN_COMPONENTS`, `CLAUDE_DESIGN_MODES`, `CLAUDE_DESIGN_REFERENCES`, `PREVIEW_CARDS`, `SVG_SANITIZED`, `CLAUDE_DESIGN_FONTS`) are never counted as drops. `FONT_SOURCE_NOT_FETCHED` is a `Warn`, so it is.

The reason codes are grouped, capped at 20 per axis and sorted by severity then count. A diagnostic carries its own `Axis`; an untagged one is mapped by `AxisForCode`, and an archive skip reason by `AxisForReason` (scripts, HTML/markup and compiled bundles belong to reference documents, images and SVG to assets, and an oversized `document.json` to tokens). The report is `{ importerId, vendor, axes: [{ axis, support, imported, dropped, reasons: [{ code, severity, count, message }] }] }`. The zip route's `report` is built from the reader's diagnostics plus the route's own facts (a text entry over its importer cap, an asset not stored or quarantined, a reference not stored, a product map not created), the kept assets and reference documents, and the **full** skipped list — the response's `skipped` field is bounded to 20 reason groups, the report's is not. So `_ds_bundle.js`, `uploads/**`, `reference/*.png` and `ui_kits/**/*.jsx` each appear as a reason with a count; the web client renders one plain-language row per axis and says "Nothing was dropped." when every row is zero.

## Zip bundles and vendor layouts

A zip archive is read only through the `import-worker` (rule 3): the API's zip import calls `POST /v1/extract-zip`, `SafeZipReader.Read` runs there, and every accepted entry is classified by magic bytes before anything is parsed. In the API, `BundleImporter` catalogs the readable entries in ordinal path order, calls `DetectVendor` to **label the archive**, and then dispatches each file: a file a registered importer's own `CanRead` claims is left to that importer, and the rest are offered to the vendor reader the label implies (a Claude Design archive with a manifest is handed to `ClaudeDesignImporter` as a whole instead of the registry). The label is one of `claude-design`, `v0`, `lovable`, `penpot`, `sketch`, or none for a plain bundle; the label is reported as an Info diagnostic with code `BUNDLE_VENDOR` and is **not** stored on `design_system_sources` rows.

- **claude-design** — labelled when `_ds_manifest.json` sits anywhere in the archive, or when a `SKILL.md` is present and the archive carries a `tokens/` tree; both rules sit above v0's `SKILL.md` rule. `ClaudeDesignImporter` reads the export (see **Claude Design exports**); when the manifest is among the allowed text entries it owns the archive and the registered importers do not also run over it. A manifest that cannot be read adds `CLAUDE_DESIGN_MANIFEST_UNREADABLE` and the archive falls back to the tolerant registry path. HTML and SVG travel only as inert text (the `markup` and `svg` channels) and a script is dropped; nothing from the archive is executed.
- **v0** — the `v0.json` layout is walked by the shared `TolerantTokenWalker`, which searches the whole tree for the recognized key names (`colors|color|palette|typography|fonts|fontFamily|radius|radii|borderRadius|spacing|shadows`, case-insensitive) and converts leaves through `TokenNormalizer`; `SKILL.md` is read with the design-md prose rules, `app/globals.css` with `css-theme`, and `package.json` for dependencies only. A script is dropped by name and never executed.
- **lovable** — labelled when the layout carries `.lovable/design-system.json` (or anything under `.lovable/`), most specific layout first; the shared `TolerantTokenWalker` converts the file, and `src/index.css` flows through `css-theme`.
- **penpot** — labelled when the root `manifest.json` names `penpot`, when a root `manifest.json` sits beside a `files/` tree, or when the archive carries any `.penpot` entry or directory; `PenpotImporter` searches the parsed tree for arrays under `colors`/`tokens`/`tokensLib`/`typography` and places colours at `color.penpot.*` and typography at `typography.penpot.*` through `TokenNormalizer`. The documented, recommended **export tokens** route (plain DTCG) needs no Penpot code and is read by `dtcg`/`tokens-studio`.
- **sketch** — labelled when `document.json` and `meta.json` are both present; `SketchImporter` reads only `document.json` (`sharedSwatches.objects[]`, legacy `assets.colorAssets[]`, `layerTextStyles.objects[]`) and never pages, layer trees or `meta.json`.

**`tailwind.config.*` is not supported from a zip.** `ZipFileClassifier` in the `import-worker` drops every `.js`, `.mjs`, `.cjs`, `.ts` and similar script entry as `DROPPED_SCRIPT`, so a Tailwind config inside an archive never reaches the `tailwind-v3` reader. Import the config as a project file instead. `BundleImporter` also reports an Info diagnostic `TAILWIND_CONFIG_NOT_READ_FROM_ZIP` when it sees one, so the archive is not silently treated as having no Tailwind theme.

Every vendor reader is **tolerant**: a leaf it cannot place is skipped with an Info/Warn diagnostic (`TOKEN_SKIPPED`, `PENPOT_ENTRY_SKIPPED`, `SKETCH_ENTRY_SKIPPED`), a document with nothing recognized answers `NO_TOKENS_RECOGNIZED`, and a bundle that yields nothing at all answers the suite-wide `IMPORT_NOTHING_RECOGNIZED` — never a crash. The worker's own `ZipInlineFileMaxBytes` cap and the `SafeZipReader` limits are the second line of defence behind each reader's 2 MiB JSON cap (see **Import worker**).

### Claude Design exports

`ClaudeDesignImporter` (id `claude-design`) reads an agent-facing export completely. It is pure: it never fetches a URL, never executes an entry and never throws — an unanticipated shape becomes an `IMPORT_INTERNAL` diagnostic and the bundle falls back. The reader keys off the format only (`_ds_manifest.json`, `themes`, `globalCssPaths`, `components`, `assets/**`), never off a customer name.

**Inputs.** The manifest is parsed with `JsonDocument` under the platform's JSON caps (2 MiB, depth 32, at most 200000 nodes). `globalCssPaths` selects the stylesheets (at most 32); a path that is not in the archive is `GLOBAL_CSS_MISSING`, and a manifest without the list falls back to the `.css` files under `tokens/`. `SKILL.md`'s YAML front matter supplies the document `name` and a fallback description. The first prose paragraph of `readme.md` becomes `voice.summary` (≤ 600 characters) and is preferred over the `SKILL.md` description, which is instruction-shaped. A script never reaches the reader from a zip (`DROPPED_SCRIPT`). HTML and SVG arrive as inert strict-UTF-8 text on their own channels (`markup`, 256 KiB cap; `svg`, 512 KiB cap, the same caps the reader enforces); the reader reduces markup to plain text and sanitizes an SVG, and never parses or executes either. An `.html`/`.xhtml` entry whose leading bytes sniff as XML is still carried as `markup` when its first element is an `<html>` root (skipping a BOM, whitespace, an XML declaration, a comment and a doctype); any other XML stays dropped. An entry over its channel cap is named in the skipped list (`SVG_TOO_LARGE`, `MARKUP_TOO_LARGE`) instead of vanishing. An entry the reader excludes by rule — `uploads/**`, `_ds_bundle.js`, `reference/**/*.png`, `ui_kits/**/*.jsx` — is reported once as `CLAUDE_DESIGN_FILE_SKIPPED` with its reason (`CLIENT_SCRATCH`, `COMPILED_BUNDLE`, `SCREENSHOT`, `NOT_EXECUTED`) and never read.

**Modes.** Each manifest theme maps its normalised `selector` to a mode named from its `label`; the base selectors (`:root`, `html`, `.light`) are not modes, and at most six modes are kept. The map goes to the CSS reader's options seam, so a `.theme-dark { … }` block imports as `modes.dark` with the block's values (`CLAUDE_DESIGN_MODES` lists the names).

**Token mapping.** The CSS reader runs over the selected stylesheets with a data-driven mapper, so no client name is compiled in.

- Colours: the reader strips the dominant vendor prefix (the most common first `-` segment of the manifest's colour token names, when it covers at least 60% of them and is 1–16 characters), then matches the canonical names exactly: `background` → `color.background`, `surface` → `color.surface`, `primary` → `color.brand.primary`, `secondary` → `color.brand.secondary`, `tertiary` → `color.brand.accent`, `brand-violet` and `brand-violet-light`, `lines` → `color.border`, `text-primary` → `color.text`, `text-secondary` → `color.text.muted`, and `success|warning|error|info` → `color.semantic.<word>`. Any other colour keeps its own `color.<slug>` path, so no token is dropped and two values never share a path.
- Type: `type-*-size` → `typography.size.*`, `-weight` → `typography.weight.*`, `-lh` → `typography.line-height.*`, `-ls` → `typography.letter-spacing.*`; `font-sans` → `typography.family.primary` and `typography.family.body`, `font-mono` → `typography.family.mono`, another `font-*` → `typography.family.<name>`. A bare weight (`400`) and a bare line height (`1.167`) take their type from the name.
- Spacing, radius, shadow and motion: `space-N` → `spacing.N`, `radius-*` → `radius.*`, `shadow-*` → `shadow.*`, `dur-*` → `motion.duration.*`, `ease-*` → `motion.easing.*`; `appbar-height`, `drawer-width*`, `content-cap`, `touch-target` and `fab-size` land under `spacing.*`.
- Derived values and stacking order: `z-*` → `z.<slug>` as a `number` token; `type-<name>-transform` → `typography.transform.<name>` as a `keyword` token; `shadow-*` → `shadow.*`, and `shadow-0: none` is stored as an empty shadow array. A `color-mix(in srgb, …)` whose two operands are each a hex literal or a `var(--name)` alias is computed to an sRGB hex colour token by `CssColorMix`; an operand that is a nested `color-mix()` or any other function is refused, not resolved recursively. A custom property that matches none of the rules above is reported once as `CSS_TOKEN_UNMAPPED` (deduped, at most 20 names).
- Explicitly unmappable, always reported: a `linear-gradient()` (`GRADIENT_NOT_REPRESENTABLE`), a `color-mix()` that cannot be resolved — an undefined alias, a cycle, or a space the resolver does not compute (`MIX_UNRESOLVED`, also `UNSUPPORTED_VALUE`) — and a `type-*` name with none of the suffixes `-size`, `-weight`, `-lh`, `-ls` or `-transform`. A `calc()` or `clamp()` value is `UNSUPPORTED_VALUE`. Every one of these is a Warn on the derived-tokens axis, and the rest of the file still imports.

**Assets.** Three kinds of file become an `ImportedAsset` (`Role`, `Variant`, `Name`, `Path`, `MimeType`, `Sha256`, `Content`).

- **Rasters.** Only an image under a segment named `assets` (case-insensitive) or the exact root `.thumbnail`, and only `image/png`, `image/jpeg` and `image/webp` by magic bytes in the worker. Caps: 2 MiB each, 16 in total, 8 per role. An image the channel cannot carry is named and left out — `IMAGE_NOT_ASSET_PATH`, `IMAGE_TOO_LARGE` or `IMAGE_CAP` — and the rest of the import continues. The exact `.thumbnail` becomes role `preview`, variant `thumbnail`. The file name names the role and variant: `maskable`, `apple-touch`, `favicon`, `icon-<pixels>`, `app-icon` (with `rounded`), `wordmark`, `logo` with `light`/`dark`, else `logo/default`; a second roleless image is `ASSET_ROLE_UNKNOWN`. A logo is then classified by `BrandLogoClassifier`: `subject` is `product`, `publisher` or `unknown`, read from the file-name tokens, the product slug and the company names found in the export prose. The slug is derived from the manifest `namespace` before `DesignSystem`, else from the `SKILL.md` name without the words `design`, `system` and `brand`. A product icon is never `publisher`; only a mark the name or prose ties to the company (or a publisher-style token such as `company` or `parent`) is, and it keeps the variant name `publisher`. `BrandLogoProfiler` measures the tone from the picture: the alpha-weighted mean colour of the PNG pixels, or of the SVG fills (an SVG with no fill is black, so dark ink). `readableOn` lists `light` and/or `dark` backgrounds where the WCAG contrast of the mark is at least 3.0. A `-light` or `-dark` token in the name is only a fallback when nothing can be measured; when it disagrees with the measurement the import reports `LOGO_NAME_TONE_MISMATCH` (Info) and keeps the measurement. The base slot (`assets.logo`) is never a `publisher` or `unknown` mark while a product logo exists.
- **SVGs.** An `.svg` entry under an `assets` segment is handed to `SvgSanitizer`, which rebuilds a new document from its allowlist and drops every other element and attribute; the stored bytes are that rebuilt document (`SVG_SANITIZED` reports how many were dropped). A document the sanitizer refuses is `SVG_REFUSED` and never becomes an asset. The role and variant rules are the same as for a raster, with `logo` as the fallback role; `ResolveLogoBase` then promotes a roleless vector to the logo base slot when no raster competes for it (or when a raster has the same stem after one trailing `-light|-dark|-icon|-mark|-vector` is removed), demoting that raster to variant `vector`.
- **Fonts.** A font under a `fonts` or `assets` segment whose magic bytes are WOFF, WOFF2, TTF or OTF. Caps: 4 MiB per entry, 8 entries, 16 MiB in total. A font the worker channel cannot carry — outside `fonts`/`assets`, over 4 MiB, beyond the entry count or the total — is dropped by name (`FONT_NOT_ASSET_PATH`, `FONT_TOO_LARGE`, `FONT_CAP`) and the rest of the import still succeeds; it is no longer a whole-import failure. A font that crosses the channel but whose magic or declared digest disagrees is `FONT_FILE_REJECTED` at the reader. The family comes from the file stem with a trailing weight/style run removed (`Inter-Regular.woff2` → `Inter`).

Before it keeps an asset, the reader re-derives the type from the magic bytes (a declared MIME that disagrees is `ASSET_TYPE_MISMATCH`) and recomputes the SHA-256 (a mismatch is `ASSET_DIGEST_MISMATCH`); the returned asset carries the recomputed digest. The worker carries the bytes verbatim on its bounded channels (see **Import worker** and [`design-system-security.md`](design-system-security.md)).

**Reference documents.** The export's prose becomes inert text documents, each bounded at 256 KiB, at most 24 documents and 2 MiB in total (`REFERENCE_TOO_LARGE`, `REFERENCE_CAP`). The path table is: `ui_kits/**/README.md` → `ui_kits/README.md`; `reference/**/*.md` and `reference/**/*.css` → `reference/<basename>`; a bare `readme.md`, `SKILL.md`, `github.md` and `_adherence.oxlintrc.json` by name; `components/**/*.prompt.md` → `components/prompts/<basename>`; and a `guidelines/**/*.html` or a root `thumbnail.html` reduced to plain text by `MarkupText` and stored as `<stem>.txt`. Every document's text passes `SecretRedactor` (`SECRET_REDACTED`), and `CLAUDE_DESIGN_REFERENCES` reports how many were kept and skipped.

**Assets and the library limit.** The zip import route stores the selected files as project files of the importing project: each is uploaded under `userFiles` with the original path `design-system/assets/<name>`, the post-upload effects (the quarantine check among them) run before the document references it, and `assets.logo`, `assets.icon` and `assets.preview` take `fileRef` = the `default` (else first-by-name) variant plus up to 7 more `{name, fileRef}` variants. A quarantined file is left out of the document with `ASSET_QUARANTINED`; when the route has no file storage or file-added effects it reports `ASSETS_NOT_UPLOADED` and imports the design without assets. The response carries the kept files as `assets` (`{role, variant, name, projectFileId}`). A font file is stored the same way but referenced from `fonts.files[<family>] = project-file:<guid>`, never from a logo/icon/preview slot. Reference documents are uploaded as project files under `design-system/references/<name>` (indexed and summarised as text, unlike a brand image) and returned as `references`; their total passes the org's upload quota. Every project file reference must name a file in the **same project** (see **Documents**).

A brand **library** can now own binary assets, but only the inert kinds: a sanitized SVG or one of the four font containers, stored in `design_system_library_assets` and referenced from a library container or a linked project as `library-asset:<guid>`. A raster is still refused (`415 LIBRARY_ASSET_TYPE`) precisely because the library route runs no image scan, so unscanned imagery never enters a shared library; rasters remain project-owned, where the CSAM/effects path already runs. `POST`, `GET` and `DELETE /api/v1/org/design-libraries/{libraryId}/assets` and `GET …/assets/{assetId}/content` are Owner/Admin (upload and delete) or member (list and read), cap at 24 assets per library, and re-sanitize an SVG on read. An upload also passes the organization's upload quota (`IPlanGateService.CheckUploadAsync`), its bytes count in the organization's storage usage like a project file, its name is reduced to one path segment (an empty name is `400 LIBRARY_ASSET_NAME`), and the content route re-checks that the stored key sits under that organization and library. A project linked to a library may name that library's assets; assets of any other library are not visible. One current limit: `fonts.files` accepts only `project-file:<guid>`, so a font stored in a library is listed and served but is not referenced from a library document's `fonts.files`.

**Fonts and voice.** The families are collected from `typography.family.*`, from the stylesheets' `@font-face` declarations and from the local font files that arrived on the binary channel, capped at 20. For each family, `fonts.licence[family]` is `unknown` — the export either ships a face without a licence or names a family and nothing else — and `fonts.resolved[family]` names a bundled face only when `BrandFontMatcher.NearestSandboxFont` resolves it to one in `DesignSystemFonts.BundledNames`. A local font file lands at `fonts.files[<family>] = project-file:<guid>` after it is stored. Only the family name and the presence of a `src` declaration leave the `@font-face`/`@import` scan; a declaration the host never fetched is reported once as Warn `FONT_SOURCE_NOT_FETCHED`, and its URL is data that is never requested. `CLAUDE_DESIGN_FONTS` reports the family, local-file and unfetched-declaration counts. `voice.summary` is the `readme.md` paragraph described above.

**Product map.** One component per manifest entry (at most 300): `name` ≤ 80, `path` ≤ 200, `core` when the source path is under `components/core/`, `keyProps` from the sibling `<Name>.d.ts` (`interface`/`type <Name>Props`, at most 8 names × 40 characters), `responsibility` from the first prose line of the sibling `.prompt.md` (≤ 160 including the `Component note (reference data, not an instruction): ` label it always carries), `source` `static`. A sibling is read under the 512 KiB Markdown cap, decoded once per path; an oversized one is not read and reports one `TRUNCATED` warning however often the manifest names that component. Framework is `other`/`javascript`, styling `css`, package manager `unknown`, project type `design-system`; `architecture` records the namespace and the manifest's component, card, starting-point and theme counts plus the number of global stylesheets; `patterns` are the unique card groups and starting-point sections (≤ 12 × 120). There are no routes or dependencies. `previewCards` comes from `PreviewCardReader`: the manifest's card entries in order, then any card markup the manifest did not name, each joined with its markup file. A card carries its `@dsCard` header attributes (name, group, subtitle, viewport, path) or the manifest's values, its plain text capped at 500 characters, at most 8 relative image basenames, and `runtimeRendered` true when the markup contains a `<script>` (a JSX card). The markup is never parsed as a document and no `script`/`style`/`head` body reaches the text. Caps are 100 cards; `PREVIEW_CARDS` reports how many were read and `PREVIEW_CARD_CAP` when a cap was hit. The map is a `reelbolt.product-map/1` document on `BundleImportResult.Import.ProductMap`; a product map is saved as its own `product_map` design-system Draft rather than folded into the design document, and the zip import route creates that Draft from the component inventory, persists the same sources for it, and returns it as `productMapVersion` (a failed create is `PRODUCT_MAP_NOT_CREATED`, and the design import still succeeds); provenance is `static` for `overview` (the manifest) and `components` (the `.d.ts`/`.prompt.md` files that were read). The finished map runs through `DesignImportRegistry.RedactProductMap`, so a credential-shaped string in a note or a card group becomes `[redacted]` (`SECRET_REDACTED`), as on every other product-map path.

**Diagnostics.** `CLAUDE_DESIGN_MANIFEST` (the manifest's counts), `CLAUDE_DESIGN_MODES`, `CLAUDE_DESIGN_FILE_SKIPPED`, `GLOBAL_CSS_MISSING`, `CLAUDE_DESIGN_ASSETS` (selected/skipped), `LOGO_NAME_TONE_MISMATCH`, `SVG_SANITIZED`, `SVG_REFUSED`, `ASSET_ROLE_UNKNOWN`, `ASSET_TOO_LARGE`, `ASSET_TYPE_MISMATCH`, `ASSET_DIGEST_MISMATCH`, `PREVIEW_CARDS`, `PREVIEW_CARD_CAP`, `CLAUDE_DESIGN_REFERENCES`, `REFERENCE_TOO_LARGE`, `REFERENCE_CAP`, `CLAUDE_DESIGN_FONTS`, `FONT_SOURCE_NOT_FETCHED`, `FONT_FILE_REJECTED`, `CLAUDE_DESIGN_COMPONENTS`, `CLAUDE_DESIGN_MANIFEST_UNREADABLE`, `TRUNCATED`, `SECRET_REDACTED`, the route's `FILE_TOO_LARGE`, `ASSETS_NOT_UPLOADED`, `REFERENCES_NOT_UPLOADED`, `ASSET_QUARANTINED` and `PRODUCT_MAP_NOT_CREATED`, plus the CSS reader's own `UNSUPPORTED_VALUE`, `MIX_UNRESOLVED`, `GRADIENT_NOT_REPRESENTABLE`, `CSS_TOKEN_UNMAPPED` and token diagnostics. Every diagnostic carries its axis, and the reader's own messages are clipped to 512 characters.

## Serving imported assets

`GET /api/v1/projects/{projectId}/design-system/assets/{fileId}` (`DesignSystemAssetController`) is the only route that serves a design-system asset inline. It answers only for a non-quarantined file of the caller's project whose stored original path starts with `design-system/assets/`, buffers at most 4 MiB, and then:

- `image/svg+xml` — re-runs `SvgSanitizer` over the stored bytes on **every read** (defense in depth); an unusable result is a 404. The response is `image/svg+xml; charset=utf-8` carrying the rebuilt document, with `CSP: default-src 'none'; sandbox` on top of the shared `nosniff`, `same-origin` and `no-referrer` headers.
- `image/png`, `image/jpeg`, `image/webp` — inline with the stored MIME under the shared content policy.
- `font/woff`, `font/woff2`, `font/ttf`, `font/otf` — `application/octet-stream` as an attachment.
- anything else — 404.

The library route `GET /api/v1/org/design-libraries/{libraryId}/assets/{assetId}/content` does the same for a library asset: it resolves the library against the caller's active organization before touching the row, re-sanitizes an SVG on read under the same CSP, and serves a font as an attachment.

## Import guard and run warnings

An import is always a Draft, so the guard is words, not a refusal. `DesignImportGuard.Assess` (Shared, pure) compares the imported document with the current approved one and adds a `Warn` diagnostic: `IMPORT_ZERO_TOKENS` when the import carries no tokens (a voice-only `DESIGN.md` is the usual cause), or `IMPORT_LOSES_TOKENS` when the approved version has tokens the import lacks (counted with `DesignDocumentDiffer.Diff`). `DesignSystemService.AssessImportAsync` runs it for `POST /import`, `/import/figma`, `/import/pdf` and `/import-zip`; the diagnostics are in the response but not in the zip report's drop counts. The import modal passes the project's real summaries to `DraftReviewBanner`, so it diffs against the current version and asks to confirm, and a warned draft asks to confirm even with no current version. The `design-md` importer reads only YAML front matter for tokens (axis `Tokens` is `Partial`); hex codes and fonts in prose or tables are not read.

A run reports the same problem: `GET /projects/{p}/executions/{id}` carries `designSystemWarnings` (`DesignSystemRunWarnings`, read at request time from the pin and the draft rows): the pinned design has zero tokens, or a Draft numbered above the pinned version already existed at `QueuedAt` and is still a Draft, or there was no approved design and a Draft waited. It never blocks a run (the customer may mean to run unbranded; a brief with `designSystem: none` is never warned). The run page shows the strings in its warnings alert.

## Export

`DesignExporter` writes an approved design document back out in three formats.

| Format | Kinds a round trip loses |
|--------|--------------------------|
| DTCG JSON (the 2025.10 `$value`/`$type` dialect) | No token value of any kind; the root `$extensions` (`modes`, `voice`, `assets`, `fonts`), every `$description` and per-token locks are exported but not read back |
| CSS custom properties | `shadow`, `typography` |
| `DESIGN.md` | `modes`, `assets`, `fonts`, `shadow`, `motion`, `component` |

**Token values of every kind survive a DTCG round trip.** The writer emits the object `$value`/`$type` dialect, and `DtcgImporter` (through `TokenNormalizer`) reads the 2025.10 object form of `dimension` and `duration` back, which also carries the composite `shadow` and `typography` values built from them, so `DesignExporter.DtcgLossyTokenTypes` is empty. A `z` number token, a `keyword` text transform and an empty shadow array survive too. The round trip is **not** a full copy of the document: the writer puts `modes`, `voice`, `assets` and `fonts` under the root `$extensions.com.reelbolt` and carries each token's `$description` and its `$extensions.com.reelbolt` (provenance and locks) through, but `DtcgImporter` reads none of `$extensions`, `$description` or locks, so a re-import has only the tokens and their values. `RoundTripTests` compares the multiset of token values per type (aliases aside), not those parts. CSS can carry colours, spacing, radii and font families but not `shadow` or `typography`; `DESIGN.md` keeps only the parts a person reads and loses `modes`, `assets`, `fonts`, `shadow`, `motion` and `component`. Export is **FREE** and writes no source row.

## Build flow

The build is a deterministic, non-LLM step type `DesignSystem`. It never throws, is retried at most once, is never cached and is **zero-rated**. It has three ops:

- `Parse` — runs the static candidates and computes coverage; writes the artifact `projects/{projectId}/agentFiles/design-system/{executionId}/step-{order}-candidates.json`.
- `Compose` — merges the static result with any LLM fallback (the style extractor's output is untrusted text: `LegacyAnalyzerMapper.DesignFrom` emits canonical tokens (`{hex, colorSpace: "srgb"}` for colours) and omits what it cannot read, and `DesignTokenSanitizer` then validates the model-built document and, per token, repairs a non-canonical `$value` through the shared `TokenNormalizer` or drops the token; every drop is a WARN diagnostic (`COLOR_UNPARSEABLE`, `DIMENSION_UNPARSEABLE`, `DURATION_UNPARSEABLE`, `FONT_FAMILY_UNPARSEABLE`, …, or `TOKEN_INVALID_DROPPED`) with the token path (redacted and clipped, as is every compose diagnostic at the artifact write; the dropped value itself is never echoed, only its length), appended to the artifact's `diagnostics` (at most 200 plus one `DIAGNOSTICS_TRUNCATED` summary) and counted in the step's `meta.diagnostics` / `meta.droppedTokens`; a model-chosen dictionary key is slugged to a valid token key, or the entry dropped with `TOKEN_KEY_DROPPED` when it looks like a secret, so one bad value never fails the paid build; model-written prose a little over its soft cap (map `architecture`, `routingStrategy`, directory purposes, entry-point roles, route titles, component responsibilities, patterns; design `voice` strings) is trimmed by `ProseClamp` at a sentence or word boundary with an ellipsis and a `PROSE_TRIMMED` WARN diagnostic (counted in `meta.trimmedFields`), while the validators themselves are unchanged and every other path (REST save, assistant) still refuses over-length values; structural problems (missing fields, bad ids or enums, control or bidi characters) and document-level violations and forbidden strings (DS_V16/DS_V20) still fail it with `DESIGN_COMPOSE_INVALID`; ingest does not persist the artifact's diagnostics), uploads `step-{order}-profile.json`, and ingests it through `POST /api/v1/projects/{projectId}/design-system/ingest`. Ingest does not replace the profile with the build: it merges the artifact over the current approved version's document (the approved version's **locked** tokens survive) and bases the Draft on that version so approving it is not a stale base. `stepOrder` is optional (omitted means the execution's `Compose` step) and must name a `Compose` step of the execution's workflow, otherwise the key is invalid; the `design` and `productMap` documents and the `sources` (project-file ids must belong to the project) are all validated before anything is written, so an invalid artifact stores nothing.
- `Require` — fails closed with `PROFILE_MISSING` unless the run's pin has both members and both pinned documents load (a missing pin, a version that changed since it was pinned, or the ambient being switched off all fail it).

The template `product-profile-from-code` ("Build brand and product profile") runs the static parse first (step 1, free). The product analyzers run **only when the product map is missing**, and the style extractor runs **only when the design is missing**; step 8 re-checks the design after the product analyzers, and everything else is free. The estimate and the cap are enforced on every route that starts this template, by one shared gate (`IDesignBuildEstimateGate`): `POST /builds`, the generic workflow Execute, Retry and Resume, the workflow-assistant execute, and the assistant's `ExecuteWorkflow` in chat and over MCP. On the workflow routes it runs after the plan's resolution cap (`402`) and concurrent-run cap (`429`) and before the credit preflight (`402`). Retry and Resume judge the run's own engine-taken snapshot (the steps that will run), not the workflow as it is now: editing the workflow after the run, or deleting it, neither lifts nor imposes the cap. A legacy run without a snapshot is judged on the live workflow. The cap is dynamic, not a fixed number: it is the cold-start high estimate of the reference profile-build template (every step of the catalog definition, no organization history), priced by the same estimator at the live prices of the models the resolver picks for the organization, times `DesignSystem:Build:FallbackCapMargin` (default 1.3, clamped to at most 10), rounded up to 2 decimals. The reference is priced by the same estimator, model resolver and price service as the actual estimate; the only difference is that it is estimated with no organization, so it is always a cold start with no organization history, while a provider the resolver picks for the organization is priced as it is for the actual estimate (a bring-your-own default Chat provider prices both at 0, so the cap is 0 and a zero-cost build passes; only a missing price is unavailable). The optional absolute ceiling `DesignSystem:Build:MaxFallbackCreditsHigh` is unset by default and, when set, lowers the cap to the smaller of the two. Measured examples at the catalog prices of 2026-10-17 (they move with prices): a cold-start build's high estimate is about 49 credits on deepseek-flash, 387 on Sonnet 5.5 and 773 on Opus 5.5, so the caps are about 64, 503 and 1005 credits. Each answers `409 ESTIMATE_OVER_CAP` above the cap (the body carries the computed `capCredits`), `409 ESTIMATE_NOT_ACCEPTED` unless the request carries `acceptEstimateCredits` of at least the high estimate, and, when billing is on but the cost estimator cannot price the build or the reference (billing on but the estimator unavailable, no model found by the resolver, or any model or price of the reference missing so a step would fall back to the seed constants), `503 ESTIMATE_UNAVAILABLE` on every route instead of treating it as free or pricing it from the seed constants. The accept-the-estimate step is the same on every route: the actual workflow's estimate against the cap. In chat the approval card shows the range and the cap and approving it is the acceptance; over MCP there is no card, so `ExecuteWorkflow` takes an `acceptEstimateCredits` argument and refuses without it. `POST /builds` also answers `409 TEMPLATE_MODIFIED` when the project's existing build workflow was edited and no longer has the build shape (the gate would otherwise skip it), asking the user to restore or delete it. The accept figure the refusal prints is the high estimate rounded **up** to 2 decimals, and the gate tolerates 0.005 below the high estimate so that echoing that figure passes. A `NaN` or negative figure is never an acceptance. In chat the acceptance needs the explicit `ChatApproved` flag on `AssistantToolContext`, which only the chat controller sets; it is never inferred from the initiator, so a new construction that omits it is not silently accepting. Any other workflow is untouched.

The `-ds` templates (`quick-win-promo-ds`, `quick-win-promo-plates-ds`) start with a `DesignSystem` `Require` step and drop the analyzer steps 1-5. `lean-context-promo-ds` is **NOT** created.

## Logos in a run

A document saved before logo metadata existed carries no `subject`, `tone` or `readableOn`. At run load the engine's `BrandAssetCatalog` measures each logo, icon and preview file it can read (PNG or SVG, at most 2 MiB each, at most 12 entries) and keeps the result for the run; a file it cannot read is listed as `unknown`. This is best effort: a failure leaves the run as it was.

- `ReadDesignSystem` with section `assets` lists the base slot and every variant with `file`, `subject`, `form`, `tone`, `readableOn`, `fileRef` and a `useFor` line, after one rule line.
- `StageProjectFile` adds a `brand` block for a staged image it recognises, plus advisory `warnings` (a company mark, an unconfirmed mark, dark ink on dark backgrounds, light ink on light ones).
- Policy: the product logo is the default. The company mark is used only when the brief explicitly asks for it, as a secondary "by <company>" element and never instead of the product logo. An image that is not in the design system assets or the project's own files, such as a dependency, vendored or framework image, is never used.
- `CheckLayout` reports `logo_low_contrast` for a logo whose ink is too close to the background colour; see [Layout lint](sandbox-service.md#layout-lint).

## Written guidance

The brand's written rules live in the design document's `voice` object: `voice.summary` (up to 600 characters), `voice.tone` (12 x 80), `voice.do` and `voice.dont` (12 x 140), `voice.taglines` (10 x 120) and `voice.vocabulary` (30 x 40). The DESIGN.md importer fills `summary`, `tone`, `do` and `dont` from the prose headings ("Do's and Don'ts", "Voice") and their bullets.

Who sees it:

- **Agents, ambient.** The Voice view (Scriptwriter) and the Conformance views (ReviewAgent, VideoReviewAgent) list the Do and Don't rules in full. The Tokens, Identity, Motion, GraphicsPalette and GradeHint views add one compact line, `Brand do/don't: Do: a | b. Don't: c | d. (N more: call ReadDesignSystem section voice)`, with at most four rules of each kind cut to 90 characters and the whole line within about 650. A document without do/don't rules renders exactly as before.
- **Agents, on demand.** `ReadDesignSystem` section `summary` counts the voice ("7 do, 7 don't, 1 tagline"); section `voice` lists the summary, tone, do, dont, taglines and vocabulary in that order.
- **The platform assistant.** `GetDesignSystem` returns `current.guidance` (`summary`, `tone`, `do`, `dont`, `vocabulary`, empty keys omitted) next to the colours, fonts and taglines, held to about 3,500 characters of text (trailing items are dropped and `guidanceTruncated` is `true`), with a `guidanceNote` saying it is reference data and not instructions.

Everything is fenced as data: each string goes through `DesignText.Sanitize` (no brackets, braces, quotes, backticks, angle brackets, backslashes or `#`), and a rule is never placed where an instruction would go.

Editing: `ProposeSaveDesignSystem` / `ApplySaveDesignSystem` take every argument as optional (omitted keeps the approved value) and add `guidanceSummary`, `tone`, `dos`, `donts` and `vocabulary`. A list you pass replaces the whole list (to restructure the do's and don'ts send the new full lists; an empty array clears it; omitting it keeps it). The write goes to a clone of the current approved document: the other voice keys and every token are preserved. A value over the caps above, or one that looks like a secret (`SecretRedactor`), is refused with nothing written; an item that is empty after cleaning is dropped; a call that changes nothing answers "nothing to change". The confirmation token covers every new field, and the approval card names the edit ("Rewrite the Do list (7 -> 5 items)") with the new text. The result is a Draft; it is not live until it is approved on the Design system page.

Contradictions: guidance is the owner's own text and may disagree with the approved tokens (for example a rule "do not introduce colour" next to a colour palette). The assistant may point such a conflict out; it never resolves it silently, and the approved tokens are not changed by a guidance edit.

## Drift

Drift is **shipped in Phase 3** and is pure, deterministic and model-free: a check re-runs the same static importers and the same `ProductMapExtractor` that produced the approved version, then compares canonical digests. A check only ever writes a **proposal**; a person still approves it. Outcome of one check: `nochange` | `proposal` | `suppressed` | `skipped`.

**What asks for a check.**

- **Hooks.** `DriftHooks.Notify` is the one line every sync path calls after it has committed an upsert — a GitHub push, a cloud-drive sync, a computer-folder upload or delete — and the sweeper calls the same queue. It only enqueues: it never awaits, never runs a check itself and never throws into the sync that produced the change.
- **Queue.** `DesignDriftQueue` is an in-process scheduler with **one lane per organization** (an unknown organization shares a single lane; at most `MaxLanes` 10000 lanes, further organizations share that lane). A lane holds at most `PerOrganizationLimit` (100) live projects, of which a periodic sweep may use at most half (50), plus a bounded memory of trailing re-runs (`PendingLimit` 100) and of refused requests (`DroppedMemoryLimit` 100). The worker serves the lanes round-robin, one project per non-empty lane per turn, so one tenant cannot fill, starve or postpone another's checks. One live entry per project: a project already queued or running is `Coalesced`, and a change made while it runs makes it run once more afterwards, so the last word wins. The debounce is **trailing-edge**: a source-triggered request for the same project within the 60-second `DebounceWindow` of its last accepted request is `Debounced`, but it is remembered and runs once when the window has passed (one timer is armed for the earliest due time over all lanes), so a pull of a hundred files is one check plus at most one trailing re-run, never a hundred and never a lost change. A `Manual` check bypasses the window and goes to the front of its own lane, but never past the lane's cap. A request refused because its lane is full answers `OrganizationBusy` and, when it is source-triggered, is remembered and re-enqueued as the lane drains; a sweep request is never remembered, because it is periodic. There is no shared global capacity any more, so `Dropped` is retained in the enum but not returned. Lanes only shrink when a check is flushed or completes. Per process, like the cloud and GitHub queues.
- **Worker.** `DesignSystemDriftWorker` drains the queue with `Concurrency = 1`, opens one DI scope (its own DbContext) under an explicit **system tenant scope** per check, bounds each check with `DesignSystem:Drift:ItemTimeoutSeconds` (default `600`, `0` disables) so one hung check cannot stall the queue, and is cancelled only by the host's stopping token — never by the token of the request that queued it. It never throws out of its loop: an unexpected failure is logged and the queue entry released.
- **Sweeper.** `DesignSystemDriftSweeper` waits 90 s after startup (so migrations and seeding finish), then every `DesignSystem:Drift:SweepIntervalMinutes` (default `360`; `0` disables it) enqueues a check of the projects that have a design system with a current version — the projects a change may have reached without an observable sync — and **expires** the proposals nobody answered within `DesignSystem:Drift:ProposalTtlDays` (default `30`), rejecting the Draft each expired proposal pointed at. The sweep is ordered by project id and runs in batches of `DesignSystem:Drift:SweepBatchSize` (default `500`) from a cursor that persists between batches; when a cycle has more projects than one batch it continues after a 2-minute pause, and only a finished cycle waits the interval. When an organization's lane has no room for the sweep's share, the batch skips that organization for the rest of the batch (the cursor never pins on it, so other tenants' projects are still swept) and **defers** the skipped projects instead of forgetting them: the next batch retries the deferred projects first, and `HasMore` stays true while any are deferred, so the cycle is not finished until they are queued.
- **Manual.** `POST /api/v1/projects/{projectId}/design-system/check`.

Triggers are `GitHubPush`, `CloudSync`, `FolderSync`, `Sweep` and `Manual`, mapped onto the proposal's `SourceChanged` / `Scheduled` / `Manual` trigger.

**Stages.**

- **Stage 0** (cheap, and the gate for both kinds) compares the current version's `design_system_sources` with the live `project_files`. A source is `Current` when its recorded `source_revision` still matches; otherwise the stored object is streamed once (bounded to 262144 bytes) and re-hashed. A file that is gone becomes `Missing`; a matching file the sources do not name is new. The result is recorded on `status` / `last_checked_at` — `content_sha256` is never overwritten, because it names the bytes the approved version was read from. Nothing changed means `nochange` and no importer runs.
- **Stage 1 (design)** re-runs the pure importers over the whole candidate set (≤ 3000 files, ≤ 262144 bytes each, ≤ 25165824 bytes total), merges the base version's **locked** tokens over the candidate (a locked token wins every collision), re-canonicalizes and recomputes the digest. Before stage 1 runs, stage 0 answers `nochange` and skips it when every changed file carries exactly the bytes (SHA-256) that a live proposal's Draft was built from, where live means `Pending`, or `Rejected` inside the `SuppressRejectedDays` window (30 days). The Draft's own source rows are the memory; the approved version's source rows are not rewritten, so once the proposal expires or the window ends the same content is proposed again. Suppressed, duplicate-of-pending and unparsable exits (nothing usable came out of the changed files) likewise write nothing to the approved version's source rows, because those rows must keep naming the bytes it was read from. An unchanged digest only refreshes the source rows; a moved digest is diffed, scored and turned into a `StaticExtract` Draft plus a `Pending` proposal. The diff compares the base against the **proposed merged document** (`DesignDocumentDiffer.DiffProposed`), not against the raw import, so a locked value that held does not appear as a change. A new proposal supersedes the older `Pending` ones for the same system and rejects the Drafts they pointed at, and Drafts are capped at 20 per system (the oldest beyond that are Rejected, except any a `Pending` proposal still points at). Rejecting still-Draft versions (superseding, expiry, the cap) re-reads each version's state and its system's `current_version_id` and touches the system row in the same save, so it is race-safe against an approval: a version approved in the meantime is never rejected. Known limitations: files that import to nothing re-run stage 1 on every push, and the importer cannot be interrupted inside a single file.
- **Stage 1 (product map)** is debounced separately: unless the trigger is `Manual` it is `skipped` while the newest source check is younger than `DesignSystem:Drift:ProductMapMinIntervalMinutes` (default `360`). It re-runs `ProductMapExtractor`, merges the extraction over the base map (`ProductMapMerger.Merge`), recomputes the canonical digest, and raises a proposal only when the score clears `ProductProposalThreshold` (`0.05`, **UNCALIBRATED**).

No stage calls a model, a chat client or an agent.

**Suppression.** A candidate whose `proposed_digest` already has a `Pending` proposal, or a `Rejected` proposal decided within `DesignSystem:Drift:SuppressRejectedDays` (default `30`), is `suppressed` and writes nothing.

**Locks.** `PATCH …/versions/{versionId}/locks` toggles a token's `$extensions.com.reelbolt.locked`. Locked tokens sit at the top of the merge precedence (see **Documents**), so a drift re-import can never move or delete a value the owner locked: the change appears in the diff, but the locked value wins in the proposed document.

**driftScore.** Both scores are `min(1, W_changed / max(4, W_base))`.

- **Design:** `W_base` sums the weight of every token in the base document; `W_changed` sums the weight of every **added, removed and changed** token path, plus `0.5` when the `voice` section changed. `DesignWeight(path)` is `1.0` for `color.brand.primary`, `color.brand.secondary`, `color.background`, `color.text`, `typography.family.primary` and `typography.family.secondary`; `0.5` for any other `color.` or `typography.` path; `0.25` for every other path.
- **Product map:** routes weigh `0.5`, components `0.1`, runtime plus dev dependencies `0.25`, on both sides of the fraction; a proposal is raised only at score ≥ `0.05`.

The weights, the `0.05` product-map threshold and the interval defaults are **UNCALIBRATED** (see **Known limits**).

## Change proposals

A change proposal is how every profile change reaches a person. It exists in the table since Phase 2 and is filled in Phase 3: a drift check, a manual check, an import or an agent write prepares the proposal, and nothing is applied until it is Approved. `GET …/proposals` lists them (with `status`, `trigger`, `driftScore` and the diff), `POST …/proposals/{id}/approve` approves the proposed version — which supersedes the previously approved version in the same transaction — and `POST …/proposals/{id}/reject` records the decision note and starts the suppression window for that digest. The sweeper moves the unanswered to `Expired` after `DesignSystem:Drift:ProposalTtlDays` (default `30`). `GET …/versions/{versionId}/diff` and the proposal's `diff_json` carry `DesignDocumentDiffer` / `ProductMapDiffer` output plus the score. Approving and rejecting are race-safe: `design_systems.current_version_id` is a concurrency token and every decision writes the system row, so two decisions that read the same system cannot both commit, and the loser answers `409 STALE_BASE`. A version that is no longer a Draft answers `409 NOT_DRAFT`, and a Draft whose `base_version_id` is no longer the current version answers `409 STALE_BASE`. A **Restore** draft is exempt from the base check (its base is the old version it copies) and so is approvable. Locks can be set only on a Draft: `PATCH …/versions/{versionId}/locks` on a version that is not a Draft answers `409 NOT_DRAFT`, so an approved version is read-only. Only an Approved version can be pinned to a run.

## Import worker

`import-worker` is a separate service (`inference/src/ReelBolt.ImportWorker`; compose service `import-worker`, internal port 8080, never proxied) that exists so that parsing untrusted zip, PDF and font bytes never happens in the API or the engine process. It holds no database, storage or provider credentials; its only secret is `IMPORT_WORKER_TOKEN`, the same value as the API's `Import:Worker:Token`, and it exits at startup when unset. It runs `read_only` with `cap_drop: ALL`, `no-new-privileges`, a 64 MiB `/tmp` tmpfs mounted `noexec,nosuid,nodev`, `mem_limit: 512m` and `pids_limit: 128`, and it sits only on the dedicated `internal: true` network `import-net`, shared with `inference` and nothing else, so it has no path to the datastores or the internet.

**Concurrency and caps.** `WorkerGate` lets `IMPORT_WORKER_MAX_CONCURRENCY` (default `2`, range 1–16) extractions run at once and takes the slot before it reads the body; any other request is answered `503` with `Retry-After` and is never queued. `pdftotext` is called with `-l`, so `IMPORT_WORKER_PDF_MAX_PAGES` (default `50`, range 1–500) pages are parsed per PDF. The API passes a busy worker's `Retry-After` through on its own `503 import_worker_unavailable`.

The API dials `Import:Worker:BaseUrl` through the named `"ImportWorker"` `HttpClient` with a 120-second timeout:

- `POST /v1/extract-zip` — `415` when the body does not start with a zip header (the API maps this to `400 NOT_A_ZIP`), otherwise one `SafeZipReader.Read`, then every accepted entry classified in ordinal path order. Script files, a `tailwind.config.*` included, never cross the boundary with their text: a Tailwind config is reported by name with empty text, and the importer answers `TAILWIND_CONFIG_NOT_READ_FROM_ZIP` so the archive is not silently treated as having no Tailwind theme. A `document.json` over the 2 MiB inline cap is dropped as `DOCUMENT_TOO_LARGE`. Two binary channels copy bytes verbatim as bounded Base64, and nothing decodes them in the worker: an image under an `assets/` segment (or the exact `.thumbnail`) whose magic bytes are PNG, JPEG or WebP, under `ArchiveAssetLimits` (2 MiB per entry, 16 entries, 8 MiB in total), and a font under a `fonts/` or `assets/` segment whose magic bytes are WOFF, WOFF2, TTF or OTF, under `ArchiveFontLimits` (4 MiB per entry, 8 entries, 16 MiB in total). An entry a channel cannot carry is added to the skipped list with its reason (`IMAGE_NOT_ASSET_PATH`, `IMAGE_TOO_LARGE`, `IMAGE_CAP`, `FONT_NOT_ASSET_PATH`, `FONT_TOO_LARGE`, `FONT_CAP`) instead of being emitted as a byte-less image or font, which the API would refuse as a bad answer. HTML and SVG travel as strict-UTF-8 text on the `markup` (256 KiB) and `svg` (512 KiB) channels; an entry over its cap becomes `MARKUP_TOO_LARGE` or `SVG_TOO_LARGE`. A `.d.ts` declaration is inlined as inert text (the component-props channel); every other script extension stays `DROPPED_SCRIPT`.
- `POST /v1/pdf-text` — PDF text extraction; `413` over its PDF cap, `415` when the body does not start with `%PDF-`, `422` when the bytes are a PDF the extractor cannot read. `ImportWorkerClient` maps an unreachable or timed-out worker to `Unavailable`, never an exception, and the token is never logged, echoed or persisted.

**API side.** `ImportWorkerClient.IsConfigured` is false when the token or `Import:Worker:BaseUrl` is blank, and both import routes then answer `503 import_worker_unavailable`. A worker `415` on `extract-zip` becomes `400 NOT_A_ZIP`; a busy worker becomes `503 import_worker_unavailable` with its `Retry-After`. The client validates every entry of an `extract-zip` answer (counts, path, digest and text bounds); any violation fails the whole answer as `502 IMPORT_WORKER_BAD_RESPONSE`, and the log line carries a fixed violation code and a count, never worker content. An entry that carries `Base64` must be an image under an `assets` segment (or the exact `.thumbnail`) or a font under a `fonts`/`assets` segment, and an SVG or markup entry carrying bytes is refused: the decoded length must equal the declared size, the per-entry/count/total caps are re-checked, and the SHA-256 is recomputed from the decoded bytes (`asset_shape`, `asset_size`, `asset_digest`, `asset_limit`, `font_shape`, `font_size`, `font_digest`, `font_limit`). `POST …/import-zip` returns a `skipped` list (up to three printable-ASCII example names per reason, with the count) and adds one Info diagnostic `FILES_SKIPPED` per reason; drops that are not one of the reader's hostile-archive reasons (for example `DROPPED_SCRIPT`, `DROPPED_HTML`, `DOCUMENT_TOO_LARGE`) are reported there instead of refusing the archive with `400 IMPORT_REJECTED`. `POST …/import/pdf` answers `404 feature_disabled` when `Import:Pdf:Enabled` is `false` (default `true`), after the project-access check. `POST …/import/figma` answers `404 feature_disabled` unless `Import:Figma:Enabled` is `true` (default `false`); it requires a `fileKey` of 10–64 letters and digits (the pattern ends with `\z`, so a trailing newline does not pass) and an access token of at most 512 characters, and `FigmaVariablesClient` reads the response body under a 2 MiB cap (not 8 MiB) and the same 20-second deadline as the request. The zip, PDF and Figma imports each persist their `design_system_sources` rows through `DesignSystemService.PersistImportSourcesAsync`.

`SafeZipReader.Read` (`ReelBolt.Shared.Archives`) is the platform's only zip reader. Limits are `MaxEntries` 2000, `MaxArchiveBytes` 33554432 (32 MiB), `MaxTotalBytes` 67108864 (64 MiB), `MaxEntryBytes` 8388608 (8 MiB), `MaxRatio` 100 and `MaxDepth` 12. Every byte actually inflated counts toward `MaxTotalBytes`, rejected entries included, and an entry whose real size differs from the size its header declares is rejected (`BOMB_SUSPECTED` or `ENTRY_UNREADABLE`). Entry names are full Unicode (accents, CJK, Cyrillic, emoji): they are NFC-normalised and de-duplicated on NFC plus invariant upper-casing (`ArchivePathRules`, shared with the API's check of the worker answer; `i`, `ı` and `İ` stay distinct), and control, format, bidi and zero-width characters, unpaired surrogates and U+FFFD are `PATH_INVALID`. The worker image (not the API image, which stays invariant and only checks the worker's answer by character class and ordinal-ignore-case duplicates) ships ICU (`icu-libs`, worker image 261 MB to 272 MB) with `DOTNET_SYSTEM_GLOBALIZATION_INVARIANT=false`; without normalisation data a non-ASCII name is refused as `NORMALIZATION_UNAVAILABLE` (fail closed). An archive aborts with `ARCHIVE_TOO_LARGE`, `ARCHIVE_INVALID`, `TOO_MANY_ENTRIES`, `TOTAL_TOO_LARGE` or `BOMB_SUSPECTED`; a single entry is rejected with `PATH_TRAVERSAL`, `PATH_INVALID`, `PATH_TOO_DEEP`, `DUPLICATE_PATH`, `NORMALIZATION_UNAVAILABLE`, `SPECIAL_FILE`, `ENTRY_TOO_LARGE`, `RATIO_EXCEEDED`, `ENTRY_UNREADABLE` or `NESTED_ARCHIVE`. On an abort, `Entries` is empty. See [`design-system-security.md`](design-system-security.md).

## Phase 3 consumers

An Approved version is used, read-only, in four places:

- **Overlays and captions** (`VideoCompile`) — `DesignSystemRunState` calls `BrandOverlayColors.Pick` to choose a font colour that clears the minimum contrast against black (a `LowContrastWarning` when none qualifies) plus the paired box colour, and `BrandFontMatcher.NearestCaptionFont` to map the requested families to the nearest available caption font, warning when it substitutes.
- **Designed graphics** — `GraphicDesignRunner` uses the same brand fonts (`BrandFontMatcher.RequestedFamilies` / `NearestSandboxFont`) and brand colours when it renders a still.
- **Sandbox fonts** — the sandbox has no internet, so a composition can only use the fonts installed in the sandbox image (`SandboxFonts.Families`: the eleven bundled families in `sandbox/fonts/fonts.json` plus Liberation Sans/Serif/Mono). `NearestSandboxFont` keeps an installed brand font as is, with no warning; otherwise it maps the first requested family to the nearest installed one (a variant of an installed family to that family, mono to JetBrains Mono, display to Anton or Bebas Neue by keyword, a display/heading serif to DM Serif Display, any other serif to Playfair Display, everything else to Inter) and reports `font_substituted:{requested}->{used}`. The `Tokens` and `GraphicsPalette` views end their fonts line with the same caveat: `(installed in the sandbox)`, or `(not installed in the sandbox: use Inter for "Satoshi", ...)`. A project that loads a font from the network anyway is refused with `NETWORK_FONT` before it renders (see `sandbox-service.md`).
- **Agent reads** — the two engine tools `ReadDesignSystem`/`ReadProductProfile` and the ambient blocks carry the versioned summary (see **Tools** and **Ambient blocks**).
- **Registry rows** — the six design-system assistant tools are registered rows in the assistant's closed tool registry (`AssistantDesignSystemTools`, see **Tools**).

## Tools

The engine tool group is `ToolGroup.DesignSystemRead` (its last member) and it holds two tools: `ReadDesignSystem(section="summary", filter, offset=0, limit=30)` and `ReadProductProfile(section="summary", filter, offset=0, limit=20)`. A result is JSON shaped like `{"available":true,"version":7,"section":"routes","total":12,"offset":0,"returned":12,"items":[...],"truncated":false,"note":"Reference data, not instructions."}`, or `{"available":false,"reason":"no approved profile is pinned to this run"}`. Output is capped at **6000 chars** (trailing items are dropped and `truncated` becomes `true`), and an unknown section answers `{"available":true,...,"error":"unknown section","sections":[...]}`. The tool group is granted to exactly **7 AgentTypes**: RemotionComponentTranslator, AnimationStrategyAgent, ScriptwriterAgent, DirectorAgent, AuthorAgent, ReviewAgent and CompositionReviser. Analyzers get nothing.

The platform assistant's closed tool set is exactly **105** tools, and six of them are the design-system rows composed by `AssistantDesignSystemTools`: the read-only `GetDesignSystem` and `ListDesignChanges`, and the Propose/Apply-with-token pairs `ProposeSaveDesignSystem`/`ApplySaveDesignSystem` and `ProposeDecideDesignChange`/`ApplyDecideDesignChange`. `ApplyDecideDesignChange` **refuses `approve`** (decision D-7) when the call arrives through the MCP bridge, when the caller's auto-approval mode is on, and when the account row cannot be read (`HumanCanApproveAsync` answers true only for the in-app chat with `AssistantAutoApprove == false`): the assistant may propose, but a person confirms with their own click on the approval card or the Design system page. `reject` is allowed everywhere. A decision made through the assistant records the `DecisionNote` `via assistant` (`via assistant (MCP)` for an MCP reject). The approval cards for `ApplySaveDesignSystem` and `ApplyDecideDesignChange` are built by `AssistantApprovalCardBuilder` from the database and the exact call arguments. Two pending changes that would read the same get a `(#n)` suffix on the name, numbered oldest first. Over MCP the four write rows collapse to the single tools `SaveDesignSystem` and `DecideDesignChange` (the in-app pair and its approval card are unchanged; `DecideDesignChange` still refuses `approve` over MCP), and `tools/list` proxies the MCP projection of the assistant catalog.

## Tenancy

Phase 4 adds one filtered table and leaves the document tables on the platform's **guard-at-parent** rule. `design_system_libraries` carries the **named `Tenant` query filter**, because the brand library is addressable by a caller-chosen id. `design_systems`, the three child tables (`design_system_versions`, `design_system_sources`, `design_system_change_proposals`) and `design_system_library_assets` carry no filter: project routes guard them at the project, and a library's container row or asset is reached only through the organization-scoped library lookup (`l.OrganizationId == orgId`). `DesignSystemService` also guards a library-scoped call itself: it loads a library container only when `design_system_libraries` names that container for the scope's organization, so a hand-built scope naming another organization's container finds nothing. A project's document may name an asset only of the library it descends from; `DesignSystemService` builds the validator's asset set from that library, never from the caller's input. New code should still go through the organization-scoped lookup rather than query `design_systems` directly. Project reads and writes go through `IProjectAccessService` on the project, needing `View` or `Edit`; a foreign or missing project is **404**, and an in-org caller whose role is too low is **403**. Library rows and their assets are scoped to the organization that owns them. Controllers are registered in `TenantBoundaryInventoryTests.ReviewedProjectRouteControllers`, and the unfiltered entities (the four document tables and `DesignSystemLibraryAsset`) are registered in the unfiltered-table theory, while `DesignSystemLibrary` is in the reviewed filtered set.

## Pricing

`Parse`, `Compose`, `Require`, import (including the Phase 3 `tokens-studio`, `shadcn-registry`, `storybook-index`, `figma-variables` and `brand-pdf` paths), the `import-worker` round trip, export, drift checks, proposals and approvals are **FREE** (`StepType.DesignSystem => (NoHold, NoHold)` in `StepCreditEstimation`; no drift stage calls a model). The LLM fallback runs as ordinary `Agent` steps and is charged through the existing path: every route that starts the template computes an estimate and requires the caller to accept the high figure (`acceptEstimateCredits >= estimate.High`), capped at the dynamic cap (the reference cold-start high at live model prices x `DesignSystem:Build:FallbackCapMargin` 1.3, optionally lowered by `DesignSystem:Build:MaxFallbackCreditsHigh`). A well-tokenized project (coverage `fallbackRecommended=false`) pays nothing.

## Known limits

- **Fallback credit cap bounds the estimate only** — the cap is dynamic: the cold-start high estimate of the reference profile-build template priced at the live prices of the models the resolver picks for the requesting workspace (its per-agent model choices included, because the resolver reads the ambient organization; the estimate is cold-start, so the workspace's run history is not read), times `DesignSystem:Build:FallbackCapMargin` (default 1.3), optionally lowered by `DesignSystem:Build:MaxFallbackCreditsHigh`; it fails closed with `503 ESTIMATE_UNAVAILABLE` when the reference cannot be priced from real catalog prices. Measured examples at the catalog prices of 2026-10-17 (they move with prices): a cold-start build's high estimate is about 49 credits on deepseek-flash, 387 on Sonnet 5.5 and 773 on Opus 5.5, so the caps are about 64, 503 and 1005 credits. It is enforced on every route that starts the template, which closes the QA-6 condition on #343. The cap bounds the estimate, not the spend: settlement still charges the actual usage of the fallback steps, including any overrun, as for every other workflow step. Parse and import stay free and unaffected.
- **Uncalibrated thresholds** — the drift weights (1.0/0.5/0.25 for design token paths; 0.5/0.1/0.25 for product-map routes/components/dependencies), the `0.05` product-map proposal threshold, the 360-minute sweep and product-map intervals, the 30-day suppression and proposal TTL windows are estimates, not measured figures. The fallback credit cap is no longer in this list: it is computed from the measured reference estimate at live prices.
- **No tombstones** — a child document cannot delete a token that came from a parent library, now that Phase 4 ships library inheritance.
- **PDF residual risk** — PDF import keeps a residual parsing risk, so the bytes are parsed only inside `import-worker` and never in the API or the engine process. (Phase 3 importers.)
- **Vendor layouts unverified** — the v0, Lovable, Penpot and Sketch layouts assume a documented structure that may not hold; each has a `BLOCKED-<vendor>.md` note. The Claude Design layout is confirmed against a real export and is documented under **Claude Design exports**. (Phase 4 zip importers.)
- **Library-owned binary assets** — a brand library can own sanitized SVGs and the four font containers (`design_system_library_assets`, `library-asset:<guid>` refs), but **not** rasters: the library route refuses an image so no unscanned imagery enters a shared library. Imported logos and icons that are PNG/JPEG/WebP therefore still live in each project's profile. A font stored in a library is listed and served but not referenced from `fonts.files`, which accepts only `project-file:<guid>`. (Claude Design import, T-010.)
