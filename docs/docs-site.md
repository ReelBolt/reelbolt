# Documentation site

The **user guide** in [`/docs/user-guide`](user-guide) is rendered by a [Docusaurus](https://docusaurus.io/) site in
[`/docs-site`](../docs-site) and served at **`/docs/`** by the root nginx. It is the only part of
[`/docs`](README.md) that is published. The developer docs (`docs/*.md`) stay in the repository and are read by
the platform assistant; they are **not** a website, public or otherwise.

## Why Docusaurus, and why only the user guide

The user guide is already Markdown with relative links, and the rest of the frontend stack is Node/React.
Docusaurus renders that Markdown as-is (`markdown.format: 'detect'` parses `.md` as CommonMark, so the
existing files' literal `{`/`<` never hit the MDX compiler) and fails the build on broken links, which
doubles as a link checker for the guide. DocFX's strengths (.NET API reference generation) are not something
these docs need.

The developer docs describe internals: architecture, security decisions, configuration keys, provider
behaviour. They are written for the people who build and run ReelBolt, not for customers, so they are not
served. They are still useful to the in-app assistant, which indexes the whole `/docs` tree
(see [platform-docs-search.md](platform-docs-search.md)) and keeps their sections as background it can
answer from without showing a link.

## Structure

| Route | Source | Sidebar |
|-------|--------|---------|
| `/docs/` | `docs/user-guide/**` | autogenerated from folders, `_category_.json` and `sidebar_position` |
| `/docs/<code>/` (for example `/docs/it/`) | the same pages translated: `docs/user-guide-i18n/<code>/…` | the same sidebar, labels translated |

That is the whole site: one docs plugin, no `developer` route. Translations are the same pages in another
language (see [Languages](#languages)), not a second guide.

**The user guide must not point at developer material.** A link from a user-guide page that leaves
`docs/user-guide` (to a developer doc, a source file, a screenshot) fails the build as a broken link: there
is no plugin that quietly turns it into a repository URL (the old `remark-repo-links` did, and was removed
because the repository is private). Write a user-guide page so that it stands on its own, and link only to
other user-guide pages.

## Running locally

```bash
cd docs-site
npm ci
npm start        # dev server with hot reload, http://localhost:3000/docs/
npm run build    # production build; fails on broken links, then runs the user-guide-only check
```

## The user-guide-only guard

`npm run build` runs `docs-site/scripts/assert-user-guide-only.mjs` as its `postbuild` step. It fails the
build when:

- a page was rendered from anywhere other than `docs/user-guide` or a known snapshot
  (`versioned_docs/version-<entry>/` for an entry in `versions.json`) (or a second docs plugin instance
  exists),
- a snapshot differs from `versioned_inventory.json` (file added, removed or changed after the cut),
  contains a file that is neither a page nor a raster image (`.webp`, `.png`, `.jpg`, `.gif`, `.avif`) a page
  shows, or `versioned_docs/` holds a directory that is not in `versions.json`,
- the docs plugin path is no longer `../docs/user-guide` (or `i18n.path` no longer `../docs/user-guide-i18n`),
- `docs/user-guide-i18n/` holds a locale that is not in `locales.json`, a folder or file that is not part of
  the layout below, or a translated snapshot that differs from `versioned_inventory.json`,
- the output has a `developer` route or file, or the sitemap lists a `/developer` URL,
- any page links to a `developer` route or to a file in the GitHub repository (`/blob/`, `/tree/` or `/edit/`).
- a user-guide or versioned-snapshot page uses a `pathname://` link, the escape hatch that skips the
  broken-link check (the old links to the developer docs were written that way).

It exists so that re-adding a developer docs plugin, or a link that resolves into the repository, cannot
reach production unnoticed.

## The dashboard link

The dashboard is at `/app` on the same origin, **outside this site's `baseUrl`** (`/docs/`). The navbar's
"Open ReelBolt" item and the footer's "Dashboard" item use `href: 'pathname:///app/'` with
`autoAddBaseUrl: false`: `pathname://` keeps them plain `<a>` links (so the broken-link check does not read
them as site routes), and `autoAddBaseUrl: false` stops Docusaurus appending `/docs` to the path. Without
the second flag the built page links to `/docs/app/`. `npm run build` runs
`docs-site/scripts/assert-app-link.mjs` after the site build and fails if any page links to `/docs/app` or
if a language (the English output and every `build/<code>/` folder) has no page that links to `/app/`.
The Italian "Open ReelBolt" link goes to `/app/` too; the dashboard picks its own language.

## Versioning and release notes

The guide is versioned with Docusaurus's own mechanism. `docs/user-guide/**` is the **`next`** working
copy; cutting a release copies it into `docs-site/versioned_docs/version-<version>/` and prepends the version
to `docs-site/versions.json`. `npm run docs:version` also captures `docs-site/versioned_inventory.json` (one
SHA-256 per file), and the postbuild guard fails if a snapshot gains, loses or changes a file after its cut.
Docusaurus serves the newest cut at **`/docs/`** and the working copy at **`/docs/next`**; the navbar
version dropdown switches between them. Old snapshots stay published and are never hand-edited — a
correction is a new cut.

Release notes are ordinary user-guide pages under `docs/user-guide/releases/`, so they version with the guide
and the snapshot contains the notes for the release it describes. A moved page keeps working through a
client redirect in `docs-site/docusaurus.config.js`.

The full procedure — editing, cutting, the release-notes template, and what is never published — is
[`docs-process.md`](docs-process.md).

## Languages

English is the source and the fallback; Italian (`it`) is the first translation. A language is data, not code:
`docs-site/locales.json` (vendored from `i18n/locales.json` by `node i18n/sync.mjs`, see [i18n.md](i18n.md))
lists the locales, and `docusaurus.config.js` builds `i18n.locales`, `localeConfigs` (label, `htmlLang`,
direction) and the navbar language dropdown from it. `npm run build` builds every locale: English at `/docs/`,
the others at `/docs/<code>/`. There is no language auto-redirect in the docs: the reader picks a language
with the navbar dropdown, and `/docs/` is always English.

### Where translations live

Outside `docs-site`, so the documentation writers' surface (`docs/**`) reaches them (`i18n.path` is
`../docs/user-guide-i18n`):

```
docs/user-guide-i18n/<code>/
├── docusaurus-plugin-content-docs/current/<same path as docs/user-guide>   translated pages (.md)
├── docusaurus-plugin-content-docs/current.json                            sidebar category labels, "Next" label
├── docusaurus-plugin-content-docs/version-<v>/ , version-<v>.json         translated snapshot of a cut (optional)
├── docusaurus-theme-classic/navbar.json , footer.json                     navbar and footer labels
└── code.json                                                               theme texts ("Next", "On this page" …)
```

The site title, tagline, alpha notice, navbar and footer labels and the copyright line are set by the config
itself from the table in `docs-site/i18n-strings.js` (English and Italian; a missing key falls back to
English). The strings in the JSON files are the theme's own and the navbar/footer twins of that table.

### Fallbacks

A page that has no translation is served in English inside the translated site (Docusaurus falls back to the
English file), so a half-translated language never has holes. Docusaurus resolves a relative `.md` link only
against the folder of the file that holds it, which would break a link between a translated and an
untranslated page; `docs-site/src/remark/i18n-links.js` therefore rewrites relative page links to the
root-relative form (`/workflows/agents.md`), which Docusaurus looks up in the translated folder first and the
English one second. It runs for the translated locales only: the English build is unchanged. A broken link in
any language still fails the build (`onBrokenLinks: 'throw'`).

### Translating a page

1. Copy `docs/user-guide/<path>.md` to `docs/user-guide-i18n/<code>/docusaurus-plugin-content-docs/current/<path>.md`
   and translate it: keep the same headings (count and order), the same front matter keys, the same links and
   code. Follow the language's glossary (`docs/i18n-glossary.md` for Italian).
2. Finish it with the stamp helper:

   ```bash
   node docs-site/scripts/i18n-stamp.mjs docs/user-guide/<path>.md docs/user-guide-i18n/<code>/docusaurus-plugin-content-docs/current/<path>.md
   ```

   It gives every translated heading the explicit id of the English heading at the same position
   (`## Titolo {#english-heading}`), so `page.md#anchor` links keep working in every language, and writes
   `i18n_source_sha` (the git blob hash of the English page) into the front matter. It fails when the heading
   counts differ.
3. Find out what needs work: `cd docs-site && npm run i18n:stale` lists, per language, the pages that are
   **stale** (the English page changed after the stamp), **unstamped**, **missing** (still English) and
   **orphaned** (the English page is gone). It is a warning by default (exit 0); CI runs it with `--strict`, so a stale, unstamped, orphaned or missing page fails the build (the `api/` folder is English-only on purpose, `ENGLISH_ONLY_PREFIXES` in the script); `--strict`
   exits 1 on anything listed. After editing an English page, re-translate the page and stamp it again.

Category (sidebar folder) labels are translated in `current.json`, not in `_category_.json`.

### Adding a language

1. Add the language to `i18n/locales.json` and run `node i18n/sync.mjs` (it refreshes `docs-site/locales.json`).
2. Add its block to `docs-site/i18n-strings.js` (title, tagline, navbar, footer, alpha notice).
3. Run `cd docs-site && npx docusaurus write-translations --locale <code>`, translate every `message` in the
   files it writes under `docs/user-guide-i18n/<code>/`, and delete the `version-*.json` files (old snapshots
   stay English). Add translated pages as above.
4. `npm run build` must pass for every locale. The root and docs nginx need no change (`/docs/<code>/…` is
   served from the same static folder).

### Versions

Snapshots `0.1.0-alpha` and `0.2.0-alpha` are English only: a translated site shows them in English.
`0.3.0-alpha` is the first cut with an Italian snapshot, so **`/docs/it/`** serves the Italian guide as it was at
that cut (a page not translated then is shown in English). Docusaurus serves the newest cut at the language root and
the working copy under `next`, so translations made after a cut appear at **`/docs/it/next`** until the next cut. When a
version is cut, `npm run docs:version <version>` also copies, for every language that has translated pages,
`docs/user-guide-i18n/<code>/…/current/` to `…/version-<version>/` and `current.json` to `version-<version>.json`
(Docusaurus does this itself; the script checks it and makes the copy if it did not), and records the translated
snapshot in `versioned_inventory.json` under `i18n.<code>.files` beside the English `files`. The postbuild guard
compares every translated snapshot with that inventory exactly as it does the English one, so a translated
snapshot is frozen at the cut too. A page not yet translated at the cut stays English in that snapshot.

### Building and serving

`npm run build` runs `docs-site/scripts/build-all-locales.mjs`, which calls `docusaurus build --locale <code>` once per
locale in `locales.json`, English first, each in its own process with `DOCUSAURUS_CURRENT_LOCALE=<code>`
(Docusaurus evaluates `docusaurus.config.js` only once per process, before it sets that variable itself, so a
single multi-locale `docusaurus build` would print English strings in every language). English lands in
`build/`, the others in `build/<code>/` (the config gives each locale an explicit `baseUrl`, `/docs/` or
`/docs/<code>/`). Both guard scripts then check every language. `npm start` serves one locale:
`DOCUSAURUS_CURRENT_LOCALE=it npm start -- --locale it`.

The docs container needs the translations too: its Dockerfile takes a second named build context
`docs_i18n=./docs/user-guide-i18n` (`additional_contexts` in compose, `build_contexts` in CI), empty when not
supplied (English only). `docs-site/nginx.conf` serves `/docs/<code>/` (no redirect for the locale root, the
locale's own `404.html`) and never redirects by browser language.

## Search

The navbar has a search box that works fully offline: the index is built at build time and queried in the
browser. No external service, no analytics, no third-party request at runtime. It uses
`@easyops-cn/docusaurus-search-local` (pinned to an exact version in `docs-site/package.json`) configured in
`docusaurus.config.js`: `language: ['en', 'it']` (English and Italian stemming), `docsRouteBasePath: '/'`,
`indexBlog: false`, `indexPages: false`, so only the user guide is indexed.

- **Per locale and version.** Every locale build writes its own `search-index.json` (`build/` for English,
  `build/it/` for Italian), holding the current docs and each cut version; the version dropdown scopes results.
  The file is fetched only when the box is first focused (several MB, cached by the browser).
- **Labels.** The plugin ships no translations; `docs-site/src/plugins/search-labels.js` supplies the Italian
  ones. A new language adds its entries there (or in that language's `code.json`).
- **Guard.** `scripts/assert-search-index.mjs` runs in `postbuild`: it loads each locale's index with the same
  lunr language packs as the browser, checks queries "dub" and "subtitles" (English) and "sottotitoli"
  (Italian) return hits, and fails if a developer route is indexed.
- The edge nginx sets no Content-Security-Policy, so nothing needs allowing; search makes only same-origin requests.

## Container

`docs-site/Dockerfile` builds the static site and serves it from `nginx:1.31.9-alpine` under `/docs/`. Its build
context is `./docs-site`; the Markdown arrives through a **named build context** `docs=./docs/user-guide`
(`additional_contexts` in `docker-compose.yml`, `build_contexts` in CI), copied to `/docs/user-guide/` in the
build stage, and the translations through `docs_i18n=./docs/user-guide-i18n` (copied to `/docs/user-guide-i18n/`). **Only the user guide is handed to this image**, so the developer docs never enter its build
context, its layers or its output. (The Inference API image receives the whole `./docs` tree through a
different named context, `platform-docs`, for the assistant's documentation search.) The root nginx routes
`location ^~ /docs/` to `http://docs:80` with the URI unchanged; the docs are public and unauthenticated.

Docusaurus is built with `trailingSlash: false`, so a page is `/docs/foo.html` and a section's folder has no
`index.html`. The docs container's `nginx.conf` therefore answers any `/docs/<path>/` with a `301` to
`/docs/<path>` (a relative `Location`); without it a public link such as `/docs/runner/` fell through to the
404 page. Verify a cut by opening `/docs/runner/`, `/docs/releases/` and `/docs/` against the built image.

```bash
docker compose up --build -d docs nginx
```

## CI

The `docs-site` job runs `npm ci`, `npm run build` (every language, with the user-guide-only guard),
`npm run i18n:test` and `npm run i18n:stale -- --strict` (fails on stale, unstamped, orphaned and missing translations)
whenever `docs/**` or `docs-site/**` changes, and the `docker` job builds the `docs-site` image from the
`docs/user-guide` and `docs/user-guide-i18n` contexts. See [ci.md](ci.md).
