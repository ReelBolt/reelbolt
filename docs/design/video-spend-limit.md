# Daily video spend limit as a user setting

1. **Owner: the user, not the organization.** The owner asked for the user settings page; a limit is a personal guard ("I do not want my runs to spend more than X today"). Credits stay the organization's ledger, and no plan caps video spend per day (the plan only decides who may generate).
2. **Storage:** one API-owned table `user_video_spend_limits` (`user_id` PK, `daily_limit_credits` null, `alert_threshold_credits` null). No row or a null limit means no daily limit beyond the credit balance and each step's `MaxSpendCredits`. Additive and expand-only; the engine maps it read-only.
3. **Gate:** `VideoGenerationBudgetGate` counts the owner's video rows of the UTC day (the user is the run's `workflow_executions.initiated_by_user_id`; audio and enhance never count) inside the same advisory-lock transaction, and refuses `BUDGET_EXCEEDED` saying a personal daily limit was reached and where to change it (Settings, Usage), with no figures: the text is stored and visible to every project member, so the limit and the use are shown only to the initiator on the Usage settings card. A run with no initiating user (a schedule) has no user limit.
4. **Platform numbers:** the per-project and the $50 global daily figures stop being limits. One very high operator safety ceiling remains (`VideoGeneration:GlobalDailyBudgetCredits`, runaway-spend protection, never shown as a limit); the ComfyUI GPU-minute caps are unchanged.
5. **Surfaces:** `GET`/`PUT /api/v1/video-spend-limit`, the Usage settings card, the estimate (`videoSpendLimit`: limit, used, left, alert reached), `GetWorkflowExecution.videoBudget`. The alert is shown in the app only: the notification pipeline is a closed set of categories mapped to Go switches, which is not small.
