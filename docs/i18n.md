# Internationalisation (i18n)

English is the source locale and the fallback. Italian (`it`) ships first. A language is **data**: a catalogue directory plus one line in the registry.

## Add a language
1. Add `{ "code": "xx", "label": "<endonym>", "htmlLang": "xx", "ogLocale": "xx_XX", "dir": "ltr" }` to `i18n/locales.json`, run `node i18n/sync.mjs` (CI runs `--check`).
2. Copy `web/messages/en/` and `site/messages/en/` to `xx/` and translate; add `api/services/email_templates/xx/`, and `docs/user-guide-i18n/xx/` for docs.
3. `npm test` in `web/` and `site/` fails on any missing key, extra key, placeholder mismatch or missing catalogue file.
No code change is needed.

## Locale resolution
- **Site** (`/`): English unprefixed, other locales under `/<code>/`. Only `/` auto-redirects (cookie `rb_locale`, then `Accept-Language`, 302, never deep links). `/?for=<persona>` additionally goes to `/for/<slug>` (or `/<code>/for/<slug>`), query kept: [marketing-site.md](marketing-site.md#languages).
- **Dashboard** (`/app`): saved user locale (`reelbolt_user` cookie, written from `application_users.locale` via `PATCH /api/v1/auth/settings`), then `rb_locale` cookie, then `Accept-Language`, then `en`.
- **Docs** (`/docs`): `/docs/` English, `/docs/<code>/` translated (language dropdown, never an auto-redirect); an untranslated page falls back to English. Pages live in `docs/user-guide-i18n/<code>/…`; how to translate, stamp and check them: [docs-site.md](docs-site.md#languages).
- **E-mail**: the recipient's saved locale, else the request locale, else English.
- Legal pages (Terms, Privacy, Refunds, Acceptable Use, Runner EULA) and the blog stay English; only their link labels are translated.

## Catalogues (web and site)
`web/messages/<locale>/<namespace>.json`, `site/messages/<locale>/<namespace>.json`. Nested JSON, ICU MessageFormat values (plural, select, `{n, number}`, `<b>rich</b>` tags via `t.rich`). One file per area so lanes never edit the same file. Keys are semantic (`files.manager.uploadButton`), not the English text. Never put markup or a price/number literal in a string.

## Code API (both apps)
```ts
import { useT, useFormat } from '@/i18n';            // client + server components (client hooks)
import { getT, getFormat } from '@/i18n/server';     // async server components
const t = useT('files.manager');                     // namespace = catalogue file (+ optional sub path)
t('uploadButton');  t('count', { count: 3 });  t.rich('terms', { link: (c) => <a href="/legal/terms">{c}</a> });
const f = useFormat();  f.number(n); f.date(d, 'short'); f.credits(millis); f.currency(amount, 'USD'); f.relative(d);
```
Non-component code never holds English text: it returns a `Msg` (`import { msg } from '@/i18n/msg'`; `msg('ns.key', { n })`) that the component resolves with `useT().msg(m)`; a lookup keyed by a dynamic value must be declared in `i18n/dynamic-keys.ts`.
Server codes: `errors.<CODE>` (API error `code`) and `failures.<CODE>` (`workflow_step_results.failureCode`) in `web/messages/<locale>/errors.json` / `failures.json`; generic HTTP/network sentences live under `errors.generic.*`. Unmapped codes show the server's English message.
```ts
import { describeError, describeFailure } from '@/lib/api/describe-error';
import { useApiErrorMessage } from '@/lib/api/use-api-error-message';
const t = useT();                                   // UNSCOPED: keys are absolute
describeError(t, err, fallback?)                     // string; code -> network -> known phrase -> server message -> status generic -> fallback
describeFailure(t, failureCode, serverText?)         // string for a step failure code
const describe = useApiErrorMessage();  describe(err, fallback?)   // hook form of describeError
```
Non-component helpers with an optional translator default to English via `lib/i18n-default.ts` (`enT`).

## Checks
`catalog.test.ts` (keys, ICU shape, placeholders), unused-key scan, glossary banned variants, `en-XA` pseudo-locale smoke (`NEXT_PUBLIC_I18N_PSEUDO=1`), ESLint `no-literal-string` on the globs in `i18n/migrated.json`.

## Italian
Glossary and style: [`i18n-glossary.md`](i18n-glossary.md). Strings the translator was unsure about go in `messages/it/_flags.json` (`{ "key": "reason" }`) and are exported for owner review to `docs/i18n-review/it.md`.

## Dashboard implementation notes (web)
- **Stack:** `next-intl` 4 without locale routing. `web/i18n/request.ts` resolves the locale per request (saved user locale -> `rb_locale` -> `Accept-Language` -> `en`, every candidate allowlisted against `i18n/locales.json`), `app/layout.tsx` sets `<html lang dir>` and wraps the app in `IntlProvider` (`web/i18n/provider.tsx`).
- **Catalogue = file name:** `web/messages/en/files.json` is namespace `files`; `useT('files.manager')` reads `files.manager.*`; `msg('files.manager.count')` takes the absolute key. Files starting with `_` (`_flags.json`) are metadata, not messages. English is deep-merged under every other locale, so a missing key shows English, never a raw key; a key missing from English too renders empty in production and `⟦ns.key⟧` plus a console warning in development.
- **Public API:** `@/i18n` (`useT`, `useFormat`, `useLocale`, `msg`, `isMsg`, types `T`, `Msg`, `Format`), `@/i18n/server` (`getT`, `getFormat`, `getLocale`), `@/i18n/config` (`LOCALES`, `DEFAULT_LOCALE`, `isLocale`, `negotiateLocale`), `@/i18n/messages` (`loadMessages`, `messagesFor`; server only), `@/i18n/dynamic-keys` (`DYNAMIC_KEY_PREFIXES`). `t.msg(m)` resolves a `Msg` (nested `Msg` values too).
- **Metadata:** in a server layout use `export async function generateMetadata() { const t = await getT('ns'); return { title: routeTitle(t('title')) }; }`.
- **Tests:** without a provider the hooks fall back to the English catalogue (`vitest.setup.ts`), so tests that assert English keep working after a component is converted. `renderWithI18n(ui, { locale: 'it' })` from `@/test/i18n` renders with the real provider (Mantine included). The pseudo-locale `en-XA` exists only when `NEXT_PUBLIC_I18N_PSEUDO=1` (and under Vitest); it is generated from English and is never in the registry.
- **Ratchet:** a migrated area records its globs in its own file `web/i18n/migrated/<area>.json` (`{ "globs": ["components/files/FileManager.tsx"] }`; `migrated.json` stays for shared entries), flags go to `web/messages/it/_flags/<area>.json`, so two lanes never edit the same file. Inside those globs `i18next/no-literal-string` (JSX text and the attributes `label placeholder title description message aria-label alt tooltip`) and `rb/no-literal-notification` (a literal `title`/`message` in `notifications.show/update`) are errors. Tests and `__tests__` are exempt.
- **Review export:** `npm run i18n:review` (in `web/`) writes `docs/i18n-review/it.md` from `web/messages` and `site/messages`, flagged rows first.

### Message payload (measured 2026-10-27, synthetic 8,000-string catalogue, 40 namespaces of 200)
| What is sent | Raw | gzip |
|---|---|---|
| Everything, every page (all at once) | 549 KiB | 92 KiB |
| Typical page, split: `common` + `errors` + one area (600 strings) | 42 KiB | 8.0 KiB |
| Heavy page, split: six namespaces (1,200 strings) | 83 KiB | 14.9 KiB |
| One namespace (200 strings) | 13.9 KiB | 3.0 KiB |

The client runtime (next-intl, use-intl, intl-messageformat) is one shared chunk of about 40 KiB raw / 12 KiB gzip in `next build` output, loaded once. Messages are inlined into the HTML/RSC payload of each page, so at launch size (a few thousand strings) all-at-once would add tens of KiB gzip to every page, including the signed-out ones. **Today the root layout sends every namespace** (the catalogue is nearly empty). When the catalogue grows, a route-group layout wraps its subtree in its own `IntlProvider` with `messagesFor(locale, ['common', 'errors', 'files'])` so only those files are serialised for it, and the root provider is reduced to `['common', 'errors']`. The hook point exists (`web/i18n/messages.ts`), no other code changes are needed.

## E-mail
Templates live in `api/services/email_templates/<locale>/<name>.{html,txt}` (14 mails); subjects and the localized footer line and fallback name are in `email_templates/subjects.json`. `MailData.Locale` picks the set; the renderer allowlists it against `api/services/locales.json` before it touches any path, and a missing locale or template falls back to `en`. Callers: saved `application_users.locale`, else the request locale (`services.LocaleFromRequest`: body field, `rb_locale` cookie, `Accept-Language`), else `en`. Invitations to people with no account and the anonymous newsletter confirm mail take an optional `locale` in the request body. The `{{.Placeholders}}` of every locale must equal English (parity test in `services/mail_locale_test.go`). Legal pages stay English. Unsure Italian strings: `email_templates/it/_flags.json` (not embedded).

### Adding a language to e-mail (code-level data)
Templates and subjects are data, but three small tables live in `api/services/mail_locale.go`: month names (`FormatMailDate`), duration units (`localizeDuration`) and organisation role names (`localizeRole`). A new language adds one entry to each; an unknown language falls back to the English text for these values, never to a broken sentence.
