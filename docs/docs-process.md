# Publishing and versioning the documentation

This is the internal procedure for the published user guide. It covers the three jobs an editor needs —
editing the current guide, cutting a release version, and writing release notes — and the rule that keeps
the developer docs off the site. The site itself is described in [`docs-site.md`](docs-site.md).

## Editing the current guide

The published guide is `docs/user-guide/**`. That folder is the working copy that everyone edits between
releases. Docusaurus renders it at **`/docs/next`**, or at **`/docs/`** while `docusaurus.config.js` sets
`lastVersion: 'current'` (see "Cutting a version").

1. Edit the Markdown in `docs/user-guide/`. Keep the writing rules in [`README.md`](README.md): plain
   language, front matter on every page, every `##` section standing on its own, and links only to other
   user-guide pages (or an absolute URL that is not repository source).
2. If you move or rename a page, add a client redirect for the old path in
   `docs-site/docusaurus.config.js` (`@docusaurus/plugin-client-redirects`) and update every link to it.
   The build fails on a broken relative link, so a missed internal link is caught; the redirect is what
   protects external bookmarks.
3. Run the local gate:

   ```bash
   cd docs-site
   NODE_ENV=development npm ci --include=dev
   npm run build
   ```

   `npm run build` fails on a broken link and then runs two postbuild guards:
   `scripts/assert-user-guide-only.mjs` (only the guide and its snapshots are published) and
   `scripts/assert-app-link.mjs` (the dashboard link is `/app/`, never `/docs/app`).
4. Commit on a branch and open a PR. Never edit `docs-site/versioned_docs/` by hand — it is a snapshot,
   generated by the cut below.

## Cutting a version

A release is cut from a green `next` working copy. The version name is the repository's **`VERSION`** file,
without a leading `v` (today `0.4.0-alpha`); the git tag is `v<version>`. One version string is enforced by
`infra/scripts/check-version.sh`, so never type a second spelling.

**A version name is only ever cut for a real release.** A docs-only `0.3.0-alpha` cut on 28 October 2026 made
`/docs/` show a version that had not been released, so on 31 October 2026 the owner had it withdrawn and the name
was cut again with the real release. To publish guide changes between releases, serve the working
copy instead of inventing a name: set `lastVersion: 'current'` and `versions: { current: { label: 'Current' } }` in
the `docs` options of `docusaurus.config.js` (Italian label **Attuale**, in `current.json`), so `/docs/` is the
working copy and `/docs/next` does not exist. The next real cut removes both and puts back **Prossima**.

Before the cut:

- the release's notes page exists in `docs/user-guide/releases/<version>.md` and is listed in
  `releases/index.md` (see below), so the snapshot contains its own notes;
- the tag `v<version>` exists on the commit you are documenting;
- `npm run build` is green.

Cut the snapshot:

```bash
cd docs-site
npm run docs:version -- "$(cat ../VERSION)"
npm run build
git add versions.json versioned_docs versioned_sidebars versioned_inventory.json
```

`npm run docs:version` runs `docusaurus docs:version` and then captures the snapshot's inventory. The
command copies `../docs/user-guide` into `docs-site/versioned_docs/version-<version>/`, writes
`docs-site/versions.json` (newest first), a generated sidebar, and `docs-site/versioned_inventory.json`
(one SHA-256 per file). Docusaurus serves the **first version in `versions.json`** — the newest cut — at
`/docs/`, and the working copy at `/docs/next`. The navbar version dropdown lists both.

The postbuild guard checks each snapshot against that inventory: a file added, removed or changed after the
cut fails the build. Never hand-edit `versioned_docs/` or `versioned_inventory.json`.

Before a version is announced, correcting it means deleting `versioned_docs/version-<version>/`,
`versioned_sidebars/version-<version>-sidebars.json` and its entry in `versions.json`, then running the cut
again; the inventory entry is rewritten. After the release is announced, a correction is a new cut.

Commit the four generated artefacts with the notes and open the PR. Verification: `/docs/` shows the new
version's announcement, `/docs/next` shows the edit you just made, and the dropdown switches between them.

**Old versions are never edited or deleted.** A correction to a released version is a new cut, not an edit
to its snapshot. Pruning old versions is a maintainers' decision; until then every cut stays published.

## Writing release notes

Release notes are ordinary user-guide pages at `docs/user-guide/releases/<version>.md`, listed in
`releases/index.md`. They are written **before** the cut so the snapshot includes them.

Derive the content from records, never from memory:

- the release record — the release, its date, commit, tag, `contains`, `excludes` and `deployed`;
- the merged PRs it names — one line each, in the customer's language (what changed for them), with an
  "Operators and reliability" group for internal-only changes.

Do not link to a pull request, a source file or the repository from a release page: the repository is
private, so a customer cannot open it. Put the public link the other way round — set the GitHub release
body to point at the notes page:

```text
https://reelbolt.ai/docs/releases/<version>
```

The template for every entry:

```markdown
---
title: ReelBolt <version>
sidebar_position: <n>
description: What <version> contains, what was deliberately left out, where it runs, and what to know.
---

# ReelBolt <version>

**Released** <date> · **tag** `v<version>` · **commit** `<sha>`

<One paragraph: what kind of release this is; alpha/beta caveat if it applies.>

## What is in it

- **<User-visible change>.** <What changed for the reader, one or two sentences.>

## What is not in it

- **<Deliberately deferred feature>.** <What ships instead, or that it is switched off.>

## Where it runs

<Hosts/commit verified, and anything about the address or certificate.>

## Upgrade notes

<Anything a tester or operator must do; "nothing to migrate" when there is nothing.>
```

Add the new page to the list in `releases/index.md`, newest first.

## What is never published

The public site is the user guide, `docs/user-guide/**`, plus its generated snapshots in
`docs-site/versioned_docs/`. Everything else in `docs/` is internal and read only in the repository or by
the platform assistant's documentation search:

- `docs/*.md` (architecture, providers, billing, configuration, these procedures), `docs/design/`,
  `docs/archive/`, operator-only files;
- source files, pull requests, and any other repository path.

The build enforces this: `assert-user-guide-only.mjs` fails when a published page comes from anywhere else,
when a `developer` route or sitemap entry exists, when a page links to a developer route or to a GitHub
`/blob|tree|edit/` URL, or when a guide or snapshot page uses a `pathname://` link. A user-guide page must
stand on its own; it never points at internal material.

The one same-origin link that deliberately leaves the guide is the dashboard: `/app` lives outside this
site's `baseUrl`, so the navbar and footer use `href: 'pathname:///app/'` with `autoAddBaseUrl: false`.
`assert-app-link.mjs` fails the build if a page links to `/docs/app` or drops the `/app` link.
